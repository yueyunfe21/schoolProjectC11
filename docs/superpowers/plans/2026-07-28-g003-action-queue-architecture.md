## 终局架构

```
大脑(×5 并行,云端,每窗一个):
  需要看  → 直接截图(观察面/直发 request,不进队;五环截图场景全部静态:
            到达规划帧、对话框 ROI、追踪面板,人物停稳后画面无变化来源)
  算好了  → 把动作(串)作为一个自包含 request 入队
  等结果  → 更新自己窗口状态 → 算下一步

执行器(×1,客户端,现已存在 = dhxy-input-action-worker + inputActionQueue):
  取队头 → 切焦点到该窗口 → 原子执行动作串 → 回报结果 → 下一个
```

**等价性原则**:turn 没有被删除,它被压缩成"队头正在执行的那一个 request"。
物理输入独占只存在执行队头的那几百毫秒,由出队纪律自动授予,无协商、无状态、
结构上不可能死锁(让权环需要"人人等人人",队列只有"排队",队头永远在被消费)。

**过期概念删除**:prepared 坐标失效的仅有两个来源都在大脑自己手里——
①自己人物未停稳(2026-07-27 已源头修复:坐标数字框 diff 判稳);
②自己前面的动作改变自己画面(大脑本来就是顺序算的)。
别的窗口的动作作用在别的窗口上;焦点切换不关对话框。
点击后的结果验证(各流程已有)保留,作为普通 request 结果,不是调度概念。

## request 的定义与固有性质(不是纪律,是架构本身的含义;2026-07-28 用户澄清)

1. **request = 一个连续性的原子动作单元**。可能是一串动作,也可能只有一个动作,但单元
   本身原子——执行器从头做到尾,中间没有任何东西能插入。需要前台连续性的交互
   (Ctrl 悬停扫描、拖拽、按住)天然就是一个 request(现状 Ctrl 扫描已如此)。
2. **request 天然短**:队列里只有动作;计算、等待、思考按定义进不了队,所以不存在
   "长 request 堵队"的问题,不需要任何时长纪律。
3. **单飞是必然而非规则**:大脑拿不到上一个 request 的结果就不知道该进哪个 phase
   (瞎子),状态机天然串行,每窗在途 request 恒 ≤1,队列深度恒 ≤5。
4. **不存在紧急动作**:本系统所有动作都是大脑正常决策的产物,无硬实时要求;
   真正的急停是客户端本地热键,不经队列。不设优先级 lane。
