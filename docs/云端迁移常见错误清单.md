# 云端迁移常见错误清单（事实链断裂族）

> 本清单来自 2026-07-23 ~ 07-28 连续多轮实机事故与 code review。**每张新卡的"新工人须知"应引用本文件**；实施任何"云端决策 + 本地感知"的功能前逐条自查。
>
> 这些错误有同一个根：**云端要动作，必须先有一条完整的事实链**——
> `本地采样(有兴趣才采) → 上报(无条件才可靠) → 云端消费(通用才不漏) → 唤醒(有事件才醒) → 决策(新鲜才对)`。
> 链上任何一环缺失，表现都是同一个症状：**角色站着不动，日志无异常**。

---

## 登记规范（强制，所有 agent 遵守）

这份文件是**活账本**，不是一次性总结。规则见 `AGENTS.md` 开头，此处定格式：

1. **写代码前**：通读本文件。
2. **查日志定位到错误后**：必须回来登记，不得只在对话里说完就算。
3. **已有同类条目 → 不新开一条，给原条目计数 +1**，并在该条目下的「现场记录」追加一行：
   `- <日期> <任务/模块> — <日志关键行或一句话现场> → <当次修法>`
4. **计数 ≥2 的条目，标题必须加 `🔴 重复 xN`**。重复本身就是结论：第一次的修法没覆盖住，该条目要当**架构问题**处理，而不是再打一个补丁。
5. 新错误按 `E<下一个编号>` 追加，标题写清**症状**而不是修法（症状才是下一个人能对上的东西）。

计数标记示例：`## 🔴 重复 x3 E5 一次性消费 / 单槽 last-wins 语义写错`

## E1 观察兴趣没发布 → 本地根本不采样

**症状**：云端等某个事实等到天荒地老；客户端日志里那个探针一次都没跑过。

**根因**：观察是**兴趣驱动**的——`CloudWholeTaskObserver.publishObservationInterests` 发布什么，客户端 `WindowObservationSampler` 才采样什么。任务实现者以为"本地探针天生就在跑"。

**实例**：五环 WAIT_COMBAT 阶段兴趣清单 `count=1`，坐标条 ROI 没注册 → 雷达退出确认要的帧永远不来 → 三个号同时死锁站桩。

**自查**：新增任何本地感知，先回答"谁把这个 interest 发布给客户端？"；跑一轮 grep 日志 `observation interests published: ... count=N`，核对 N 与预期一致。

## E2 只认专属信号，看不见通用情况

**症状**：功能在"专属场景"能跑，在最常见的普通场景完全不动。

**根因**：把"本任务的专属标记"当成了通用流程的前置条件。

**实例**：
- `XinshouTask.shouldReadTracker` 要求匹配到 7 张新手专属 title 之一才读 tracker 面板 → 普通任务标题时永远读不到面板 → 0 绿链 → 死循环 park；
- `preparedXinshouOption` 只认 `source` 以 `xinshou:` 开头的 prepared action，**而没有任何生产者产出它** → 对话框弹出也视若无睹。

**自查**：写下"这个条件为假但业务仍需推进"的场景，逐个确认有出路。凡是"专属标记"，问一句：它该门控**整条通用循环**，还是只门控**该节点的专属处理**？（几乎总是后者。）

## 🔴 重复 x2 E3 把凭据/claim 当成上报的门，而不是分类标签

**症状**：物理事实明明发生了，云端一无所知。

**根因**：`publishCombatEdgeIfClaimed` 式设计——"没有预登记凭据就不上报"。事实是客观的，凭据只应回答"这个事实是预期的还是意外的"。

**实例**：修罗看打点击才注册凭据 → 五环、偶遇战斗全无凭据 → 本地明明用放大镜锚点确认了退出，边沿发布被拒 → 云端永久 IN_COMBAT。

**铁律**：**物理事实无条件上报**；凭据/身份只做标签与围栏（observation run/window/tenant 身份该拦的仍要拦）。

**现场记录（追加）**
- 2026-08-02 修罗窗口 `hwnd-8D216DA` 第 2 轮 — 本地实际点击看打后已上报 `IN_COMBAT` / `COMBAT_EXITED`，两条边沿均带同一 local claim 与 generation=2；Cloud 却因自己的 `expectedClaim` 账本为空而拒绝两条物理事实，修罗停在 `WAIT_TRACKER_SHORTCUT_PATHING` 直到 180 秒 watchdog。→ 删除 Cloud 的第二份 claim 账本：Cloud 仅以当前窗口 binding 中的 active combat generation 配对进/脱战；本地 claim 只保留为 expected/unexpected 的分类标签，不能再成为 Cloud 接受物理边沿的前置条件。

## 🔴 重复 x3 E4 无限期 park + 单一证据源无兜底

**症状**：任务永久挂起；暂停后恢复不生效；watchdog 到点才动。

**根因**：`timeoutMs=-1` 裸挂，或退出/推进判定依赖唯一一个可能永远不来的信号。**变体：那个唯一信号源会被另一个业务状态（如战斗）物理遮蔽**——遮蔽期间判定永远出不来，而系统两边都在"正确地"等。

**实例**：
- `WAIT_COMBAT` 无限 park，暂停/恢复指令无法唤醒（park 中不跑检查点）；
- 雷达退出确认强制要求"小地图可读"，而该帧的兴趣没注册（见 E1）→ 信号缺失 234 次仍 keep IN_COMBAT。

**铁律**：**park 一律有界**（≤25s 循环再挂）；**每个可能结局都要有对应唤醒事件**；关键判定给出降级路径（证据远超阈值时允许放行）。**判定所依赖的证据源如果会被某个状态遮蔽，必须在进入那个状态的边沿上直接给出结论**——那个边沿本身往往就是答案。

**现场记录**
- 2026-08-01 G005 天庭 round=3 — `inCombat=true` 持续到约 192 秒，但 `runSubtasks()` 在读取战斗事实前直接按绿链后的 `subtaskStartedAtMs` 触发 watchdog，转入 `RETURN_HOME` 并实际使用两次回城道具。→ watchdog 改为先读取事实；首个 `IN_COMBAT` 清零 watchdog，脱战后只能由新的 tracker 事实重新建表，战斗期间只允许 `PARK_COMBAT`。
- 2026-08-01 G005 天庭战后队员离队 — 旧代码把 `waitForMembersReturnIfNeeded()` 的 120 秒超时当作“可继续”，且没有开放 `TEAM_RETURN`，队长会带剩余队员继续战斗。→ 战后归队改为修罗同类相位门：确认有 leader return signal 时开放 `TEAM_RETURN` / `COMMON_BOX`、释放 leader task turn、短周期复查；信号未消失不得绿链或导航。整轮结束则先确认回城成功，再在天宫等待归队。观测未决一律 fail-closed，不能当 ABSENT。
- 2026-07-30 G005 天庭战后不动 — 绿链→走路→对话框→进战，走路 intent 全程 ACTIVE：pathing 终态**只靠坐标条**判，战斗把坐标条遮了、战后重绘又反复清零"站稳"计时，实测**战斗结束后 61 秒**才判出 STOPPED_AWAY。这 61 秒里云端按 E17 正确拒清 ACTIVE、观察面按规矩不发绿链 → 战后恢复整体卡死，绿链过期（ageMs 51s→138s）、6 pass 无进展、整轮 completedRounds=0 结束，角色站桩。→ 客户端 `WindowObservationSampler` 在**进战边沿**上直接收尾：ACTIVE/UNKNOWN 的 intent 置 STOPPED_AWAY（"combat entry ended the walk"），已终态/无 intent 不动；`CombatEntryEndsPathingLegContractTest` 3 条钉死。人打起来了=走路必然结束，这个事实采样器当场就有，不该让它由被遮住的坐标条一分钟后猜出来。
- 2026-07-31 G004 野外战斗第 4 次战后站桩 — `16:59:36` Runner 已维护 Auto+8；之后到停止前，所有巡逻右键均被本地硬闸以 `COMBAT_ACTIVE` 拒绝。前 3 个战斗代次可恢复，说明循环与队列可用；第 4 次未发布 `COMBAT_EXITED`。根因是放大镜 `20x22` 单锚点未命中后，即使战斗模板也明确未命中，状态机仍无限保留 `UNKNOWN`。→ 保留放大镜正证据；补“放大镜与战斗模板皆 ABSENT = 脱战”反证；任一采集 UNAVAILABLE 仍不放行，避免把截图失败当脱战。

## 🔴 重复 x4 E5 一次性消费 / 单槽 last-wins 语义写错

**症状**：该做一次的做了很多次；该并存的两个事实互相吞掉。

**根因**：用单个字段存"最后一次"，而不是用集合存"已消费"；或多个事实挤同一个 factType 槽被 latest-wins 覆盖。

**实例**：
- `esc_bot` 被 title 命中吞掉（单返回值优先链）→ 拆成独立 fact 才修好；
- REPAIR 走提前 return 从不进 `consumedTitles` → title 抖动一次就重放整套三件宏；
- `CloudXiuluoLocalClickState.consumeClicked` 用 `getAndSet(null)`，不匹配也清空 → 看打事实被错拍查询静默丢弃。
- 修罗 local `kanda2` 的 attempt claim 在首次物理点击成功后一直保持；未见 `IN_COMBAT` 时没有“本次点击未生效”的释放/重试转换 → 后续模板命中全被 `claimed=false` 拦下。

**现场记录**

- 2026-07-30 修罗 round=8，`13:59:39.248` local-kanda claim=true，`13:59:39.863` 已实际左键 `(1550,623)`；此后同一 attempt 的模板仍持续命中，但从 `13:59:45.165` 起反复 `claimed=false`，且没有 `IN_COMBAT`。→ 现有“最多三次 saved-green re-press”只在 `PATHING_TERMINAL + CLOUD_NO_ACTION` 分支，未接住 local-kanda 点击后未进战；需把未进战结果纳入同一有界 retry/fallback 链。已修为：每次实际看打后等四个 Runner 战斗采样，最多三次本地看打；耗尽才上报 Cloud，由 Cloud 重按绿链并产生新 attempt。

**自查**："这两个东西会同时出现吗？"会 → 各自独立槽位/独立 fact。"这个动作重复执行有害吗？"有害 → 用 consumed 集合，且**所有成功路径**都要登记。**"旧占位会不会挡住新事实的发布？"会 → 消费者按新鲜度拒收的东西，发布者一侧必须能清掉，两侧的过滤规则要对齐**。

**现场记录（追加）**
- 2026-07-31 抓鬼第 5 只不动（战斗结构收敛后的接缝）— 「进战即清看打状态」落地后，`CatchGhostTask` 的 STOPPED_AWAY 终态分支还按旧寿命假设"Runner 探针永远武装着"，只等不重挂；且该分支**不消费终态**（ARRIVED-target 分支消费、它不消费）→ 保留态事实每拍重发把 phase 锁死在"等 kaida"，云端不再 arm，客户端每秒 `Local-kanda probe blocked: reason=no-schedule`。教训：**把某个状态的寿命改短之后，必须 grep 所有"假设它还活着"的等待分支**——和"改共享层必须扫全部消费者"是同一条纪律的另一面。→ 该分支补两针：消费终态（清 intent，杀掉重发自旋）+ 幂等重挂本轮 enter-battle interest/schedule（open/replace 同轮身份无害，WAITING_FOR_COMBAT 防重复看打）。
- 2026-07-30 G005 天庭一轮做完站桩 — 22:08:40 一轮完成、title 消失，应走「回城道具」（业务 §7/§8）。观察面每拍都读出 title-miss 负结果，但 `CloudWholeTaskObserver` 的负结果分支 `if (existing != null) return;` —— **战前的旧 tracker 链接一直占着 prepared 槽，每一条负结果都被吞**；任务侧又按年龄拒收那条旧链接（日志 `ignoring a stale tracker link ageMs=25s→173s`）→ 任务看到"无链接也无负结果"，`panelRead` 永远 false，`RETURN_HOME`（要求 `panelRead && !titlePresent`）结构性不可达 → `PARK_IDLE` 空转。两侧各自"正确"过滤，合起来把事实链掐死。→ 负分支里对必然已 stale 的占位 `clearIfMatches(TASK_TRACKER_PATHING, …)` 后照常发布负结果；`TiantingTitleGoneReachabilityContractTest` 钉死"槽被旧链接占着时负结果不得被吞"+"RETURN_HOME 仍要求真实 panelRead"。
- 2026-08-05 G019 五环暂不可用 Story — `hwnd-49C017C` 的 5 秒 Title gate 正确超时后，Observer 已把
  当前画面识别为 `STORY`，并发布 `VERIFY_WHITE_TEMPLATE / wuhuan.temporarilyUnavailable`；任务重判却固定
  调 `inspectPreparedDialogType(...)` 按 `INSPECT` 消费，日志明确为
  `prepared dialog consume mismatch ... mismatch=operation operation=INSPECT`，随后错误返回 `type=NONE`。
  → 生产者和消费者必须对同一 operation 做显式分派；模板 replay 只能证明识别算法，不能代替
  `publish -> ready -> exact consume -> click -> phase handoff` 连通性合同。
  已返修：Title 超时分支不再先做 `INSPECT`，而是直接按 prepared action 的真实 operation 分派；合同禁止把
  operation mismatch 再映射为视觉 `NONE`。

## E6 双仓共享协议文件不同步

**症状**：客户端上报被云端 400 拒绝；或反之。

**根因**：`com/bot/dhxy/cloud/turn/protocol/**`（含 `observation/`）两仓各有一份，必须 **byte-identical**。改一处忘了同步另一处。

**自查**：每次改协议后跑
```bash
diff -r --strip-trailing-cr DHXY-cr271/src/main/java/com/bot/dhxy/cloud/turn/protocol dhxy-cloud-brain/src/main/java/com/bot/dhxy/cloud/turn/protocol
```
另注意：**新任务加入白名单**时，validator 里往往有多处独立的任务码判断（turn 协议一处、observation 协议一处），漏一处就是运行时 400。

## 🔴 重复 x3 E7 拿过期缓存做决策

**症状**：云端拿几分钟前的状态决策，行为完全脱离实际画面。

**根因**：迁云后位置/状态来自 turn 采样，可能长时间不刷新；而代码沿用了本地时代"缓存永远新鲜"的假设。

**实例**：`navigateToTaskNpc` 用缓存位置判"NPC 就在旁边→跳过导航直接点击"，实际角色在另一张地图 → 对着错误的 NPC 狂点 137 秒。

**自查**：任何"用位置/状态走捷径"的分支，加**新鲜度门**（超时则强制重新同步）。**"年轻"不等于"新鲜"：跨过一个改变画面的事件（战斗/换图/翻页）之后，比事件早出生的证据无论多年轻都是旧的——年龄门之外还要有"不得早于事件"的下限门。**

**现场记录（追加）**
- 2026-07-30 G005 天庭战后点空绿链 — 战斗 22:24:50 结束，观察面用**面板还没重绘**的帧发布了链接（出生几秒、轻松过 10s 年龄门），22:24:57 点击 `(398,316)`＝旧面板绿链的正确位置、新画面上什么都没有 → proof negative。同一坐标此前三次全部成功，问题不在坐标计算，在**帧比画面旧**。→ 战后恢复完成时打 `trackerLinkNotBeforeMs` 下限，`freshTrackerLink` 拒收比它早出生的链接（天庭观察面对仍在面板上的链接总是**重发带新 preparedAtMs**，拒收只多等一拍不会死锁）；publish/click 两侧补坐标+年龄日志（E18）。
- 2026-08-04 G005 天庭 `03:41:53` 战后约 12 秒才点绿链 — 任务在 `25s` park 超时后按旧的 `IN_COMBAT` 事实进入周期维护；Client 在维护启动约 `1s` 后已确认脱战并于 `99ms` 内发布 `COMBAT_EXITED`，但已下发的 generic-window 清理、左上状态探针、全窗自动面板校验与 `Alt+8` 刷新没有脱战检查点，继续串行执行约 `6.6s`。迁移版 `CLIENT_RUNNER_EXIT` 分支只读异步 `GameContext`，不再像基线 `696a12b0` 那样在 tick 开头同步 `checkAndSyncCombatState()`；一次旧判断因此可跨越脱战边沿继续产生动作。随后原 E7 修复又在**恢复完成时**才设置 `trackerLinkNotBeforeMs`，把脱战后 `0.34s` 已准备好的正确绿链一并判旧，再等观察面 `1.79s` 重发。→ 战斗维护的每个耗时阶段必须在继续下发动作前重查 exact combat edge/state；时间下限应表达“不得早于有效画面代次”，不能用恢复链结束时间误伤脱战后已经属于新画面的证据。

## E8 taskRunId 双格式身份不匹配

**症状**：登记成功、消费永远失败；功能静默空转。

**根因**：观察面 id = `remote-turn-xxx`（无后缀），业务面 id = `remote-turn-xxx:0:TASKCODE`。两边混用则永不相等。

**自查**：任何跨观察面/业务面的身份比较，明确用哪一种，必要时两个都存。

## 🔴 重复 x4 E9 长耗时/慢依赖操作占错了线程或关键路径

**症状**：某窗口在宏执行期间所有感知停摆，云端对它致盲十几秒；或主流程在一个"锦上添花"的步骤上白站几十秒。

**根因**：把背包/修复等 10s+ 的宏直接在 `dhxy-observe-*` 线程执行；或宏体在 `synchronized` 块内，采样线程下一周期撞锁（**换个位置≠解除阻塞**）。

## E21 把“配置时长自然结束”伪装成“人工停止” → 队列后续任务被截断

**症状**：任务自身按配置时长结束的日志正常出现，但同一启动队列中排在后面的动作（例如“睡眠电脑”）完全没有执行。

**根因**：任务把“已完成自己配置的工作量/时长”返回为 `TaskRunResult.STOPPED`。Cloud turn runtime 的 `STOPPED` 是取消语义：它会立刻 `break`，不再执行队列的下一项；这和用户点击停止、任务收到 stop token 的语义必须严格区分。

**铁律**：自然达到任务配置的次数、时长或完成条件时，返回 `SUCCESS`；只有用户停止、stop token、线程中断或显式取消才返回 `STOPPED`。队列续跑依赖这个返回合同，不能只看任务自身的“结束”日志。

**现场记录**

## 🔴 重复 x2 E22 自堵型等待：等待期间挡住了让被等事实产生的前置动作

**症状**：一个 bounded wait **每次都恰好超时**，超时后重试却在几秒内成功。看日志像"偶发慢"，实际是"这个等待在结构上不可能成功"。

**机制**：等待写在一个 pass **内部**，而让被等事实产生的前置动作写在**下一个 pass 的开头**。等待期间 pass 不结束 → 前置动作永不执行 → 事实永不产生 → 只能超时。超时使 pass 重启，前置动作这才跑，于是"重试很快就成了"——这个**超时后立刻成功**的模式就是本类错误的指纹。

**与 E17 的关系**：E17 是"清早了"（ACTIVE 时清，把活体删了）；E22 是"清晚了"（终态残留留到下一 pass 才清，把观察面堵着）。同一个 `releasePathingIntent` 两头都能踩，**改一头时必须同时验另一头**。

**判据（三问的第三问，最容易漏的那一问）**：
- 我要等的这个事实，**由谁发布**？
- 它发布的**前置条件**是什么？（如：观察面要求 pathing intent 已清）
- 这个前置条件**由哪段代码满足、那段代码在我等待期间跑得到吗**？
  跑不到 → 前置动作必须移进等待循环内部，不能留在下一 pass。

**修法**：等待循环第一件事就是满足前置条件（幂等 + 成功后置 latch 不再重复调用）；不要指望"下一轮 pass 会处理"。

## 🔴 重复 x2 E23 预算的计量单位和它想约束的东西不是一回事（bound 混尺度 / pass 当时间用）

**症状**：
- 快问题（"点击有没有生效"）被慢问题（"面板刷新了没有"）的预算拖着，一次失败的点击要几十秒才重试；或
- 反过来：**按"次数"计的预算在事件风暴里几秒烧光**，设计者以为的两分钟实际只有二十几秒。

**机制**：
- `awaitX` 里 peek 了两件事却只有一个 deadline，取值必然向慢的那个靠；
- 或预算按 **pass 数**计，而一个 pass 的时长 = park 被唤醒前的时长——唤醒频率变了，预算的真实时长跟着变 10 倍以上。**pass 不是时间单位。**

**判据**：
- 一个 wait 里 peek 了几种证据？到达时间同量级吗？不是 → 拆两段 bound。
- 每个 `++passes > LIMIT` 形式的预算：问"一个 pass 最短能多短？"若唤醒事件可以连发，这个预算就是假的 → 改成 `now - sinceMs > TIMEOUT_MS`。

**配套铁律（park 粒度）**：deadline 只在两次 park **之间**检查，所以 **park slice 必须显著小于它所服务的 bound**，否则 bound 是假的。新增 bound 时**必须同时指定与之匹配的 slice**。

## 🔴 重复 x2 E24 把"动作没产生预期事实"当成"再做一次" → 物理动作死循环

**症状**：同一个点击每隔几秒重复一次，永不停止。决策日志是固定短循环（如 `CLICK_X → PARK_IDLE → PARK_IDLE → CLICK_X`），每条事实都一模一样。

**机制**：状态机靠"动作产生的事实"推进（点击 → 走路 → 到达 → stopped）。但有一类**合法**情况动作本来就不产生事实——**目标已经在脚下，点了当然不动**。客户端的动作证明机制（start proof）看不到位移就**什么都不注册**，于是终态事件永远不会发布，`stopped` 永远 false，决策看到"没在走 + 没停下 + 链接就绪"，只能再点一次。

**连锁**：后续所有挂在那个未达成状态背后的分支（本例的暗雷/对话/回城）**在结构上不可达**——不是逻辑写错，是根本走不到。排查时容易误判成"暗雷逻辑有 bug"，实际是前一格没翻过去。

**判据**：对每个"发动作 → 等事实"的环节问：
- 有没有一种**正常情况**下这个动作本来就不产生事实？（目标已在脚下 / 已经是目标状态 / 对方已经关了）
- 那种情况下状态机会怎样？——若答案是"回到发同一个动作"，就是本条。

**修法**：动作的返回值必须带上"**事实到底有没有产生**"，而不只是"命令有没有执行成功"。命令 COMPLETED 只说明鼠标按下去了。产生不了事实 = 已经在目标态，按"已到达"处理，不要重发。确认要按 id 而非 source（同类动作 source 相同，会误认上一段的残留）。

## 🔴 重复 x3 E25 服务注入了、构造器接了，但驱动它的每拍 tick 从没被调用

## 🔴 E26 park 的唤醒集合太宽 → 被无关事件反复叫醒,在上一条腿还在飞的时候重新规划

**症状**：同一个目的地被导航两次,中间只隔几秒。第二次的物理动作(开地图/搜地名/点路线/点小地图)全都白做,而且**会把正在走的那条腿从半路重新起点**。用户看到的就是"队长又点了一次小地图"。

**这不是设计的问题,是没按设计做。** 设计对每个 park 都规定了唤醒集合,复用别处的集合等于把契约扔了。

**判据(和 E22 是一对)**：
- E22 问的是"我等的事实**来不来**"(自堵型等待)；

3. 再在 pass 顶部加**前置状态检查**(上一步还在进行中就站下),让规则不依赖某一条唤醒路径;站下要有预算(E16)。

## 🔴 E31 启动被云端拒绝后，错误要求等待“已接受任务”的终态才允许重启

**症状**：第一次点击启动因前置条件（例如未组队）收到明确的
`TASK_START_REJECTED`，这是正常失败；用户补齐条件后第二次点击启动，所有窗口却立即回到空闲，
日志为“清理旧任务失败，云端未确认终止，保留远程 turn loop”。

**根因**：`WindowTurnLoop` 已在首次 HTTP 拒绝后停止，但 `TurnModeGuard.canRemoveStoppedLoop(...)`
只允许两类 loop 删除：无 `TurnTaskStartRequest` 的 transport loop，或已经收到 Cloud task terminal
的已接受任务。`TASK_START_REJECTED` 发生在 Cloud 接受前，没有 task terminal；把它和“已接受但
transport 中断、可能仍占 RunSlot”的不确定失败混为一谈，导致停止的 rejected loop 永久留在 registry，
挡住下一次合法启动。

**铁律**：必须区分三种 start 结局：
1. Cloud 已 ACK 接受：只能等同一 `startRequestId` 的 terminal，不能贸然删 loop；
2. Cloud 明确 `TASK_START_REJECTED` 且尚未 ACK：Cloud 没有 RunSlot，可在 loop 停止后直接移除；
3. 未知 transport/timeout：保留 exact loop/请求，避免创建第二个 startRequest。

**现场记录**
- 2026-07-30 天庭：`19:30:17` 第一次未组队启动，五个窗口均收到
  `TASK_START_REJECTED: 队伍身份识别失败：tooltip OCR 未返回可用队长 ID`，每个 turn loop 已停止；
  `19:30:58` 组队后第二次启动，五个窗口均被本地
  `云端未确认终止，保留远程 turn loop` 拒绝，新的 Cloud start 根本没有发出。
  修复：仅为“Cloud 明确拒绝、尚未 accepted ACK”的 loop 记录可安全移除的 start-rejected
  终态；`canRemoveStoppedLoop` 放行这一精确状态，不能把所有 `lastFailure != null` 一概删除。
  Client 现将 HTTP problem 的结构化 `code` 保留到 `TurnTransportException`，仅
  `HTTP_STATUS + TASK_START_REJECTED + pre-ACK` 会立即移除 registry loop 并清理窗口 transient
  state；timeout / network / 其他 HTTP error 仍保留同一个 request。Fresh gate：第一次故意拒绝后，
  第二次合法启动必须发出新的五个 startRequest，日志不得再出现“云端未确认终止”。

## 🔴 E30 把"次数型"的兜底值套用到"时长型" → 无限变成 1 分钟，看起来像集体掉线

**症状**：多个窗口在启动后一两分钟**同时**结束，外表和"全部掉线"一模一样。日志其实写得很清楚（`自动战斗达到配置时长 durationMinutes=1`），但因为是同时发生，第一反应都是去查网络/崩溃/新改的代码。

**机制**：一个通用的 `normalizeRunCount(count)` 对空值/负值返回 **1**——这对"跑几次"是合理兜底（至少跑一次），对"跑几分钟"是灾难：业务上 `0 = 无限`，兜底成 1 就是**把无限改成了一分钟**。当某个任务从"写死无限的标签"被改造成"可编辑数值"时，就会一脚踩进这个通用兜底。

**判据**：任何 UI 数值控件，先分清它是**次数**还是**时长/容量**。
- 次数型：空值兜底 1（"至少做一次"）。
- 时长型：空值兜底 **0 = 无限**（"没说就是不限"）。
两者**不能共用同一个 normalize 函数**。

**修法**：给时长型单独一个 `normalizeDurationMinutes`（null/负 → 0），并把编辑器的 `parseNonNegativeInt(..., fallback)` 的 fallback 也按类型分开。

**现场记录**
- 2026-07-30 自动战斗 — 四个队员窗口 `16:20:10` 启动、`16:22:20` 同时 `自动战斗达到配置时长，结束任务 durationMinutes=1 → result=STOPPED`，用户判断为"一进战斗全部掉线"。根因：工作区里有一处未提交改动把 `AUTO_BATTLE` 从写死的 `taskCountSummaries.put(AUTO_BATTLE, "无限")` 改成可编辑时长，于是走进了 `normalizeRunCount(null|<0) → 1`。业务定义**自动战斗 default 就是无限**。→ 新增 `normalizeDurationMinutes`（→0），`syncTaskRunCountToProperties` / `normalizeInlineTaskCount` / 编辑器 fallback 三处按 `isDurationTask` 分流。相关：`AutoBattleTask` 自然到时仍返回 `STOPPED`（见 E21，未修）。
- 2026-07-31 江湖历练队员 — 任务次数 `1` 在队员改派 `AUTO_BATTLE` 时被原样复用，
  `AutoBattleTask` 因而解释为 `durationMinutes=1` 并提前 `SUCCESS`。→ Cloud 改派点统一将
  非显式 `AUTO_BATTLE` 的队员配置固定为 `0`（无限）；仅 UI 直接启动自动战斗允许时长。

## E31 OCR 单字误读 × 精确匹配门 → 系统拒绝点击它自己刚搜索出来的目的地

**症状**：世界地图搜出路线、终点黄链就在面板上，点击前复核却报 `WRONG_DESTINATION`，两次重试全拒，导航 `MAP_NOT_REACHED`，角色站在地图前。

**根因**：本地 OCR（单 provider，无 Baidu 兜底——这是用户批准的云端差异）把一个字读成形近/同音字：`东海渔村` → `东海鱼村`。复核的模糊打分只认"连续公共子串 ≥ 60%"，错字在名字**中间**时连续段被切碎（东海=2 + 村=1 < 要求 3）→ 0 分 → 拒点。编辑距离明明是 1，打分函数算了距离却不用它。

**判据**：`expected=X actual=Y` 且两者**长得几乎一样**（编辑距离 1）→ 是 OCR 错字，不是走错地方。证据链先行：本条能一次定案，全靠前一天补的 miss 落盘（raw.png / yellow.png / ocr-words.txt），**一次复现直接看到 `东海鱼村@(284,111)`**，零猜测（E29 纪律的直接回报）。

**修法（用户拍板：走既有纠错，不放松匹配器）**：OCR 读数在判错**之前**先过 `MapNameCanonicalizer`（`config/maps.json` 全量地图字典，与 tracker/小地图地图名同一套纠错）。字典纠错比通用编辑距离容错**严格更安全**：`东海鱼村` 里的「鱼」不在任何地图名里 → 纠正为 `东海渔村`；而读成 `长寿` 时它本身就是真实地图 → 原样保留、继续对不上期望的 `长安`——通用容错做不到这层区分。`DecisionEngine.matchesExpectedRouteDestination` 统一三处比较（direct/wrapped/exact-gate）；最初实现的 `CloudOcrTextMatcher` 编辑距离分支**已撤销**。`RouteDestinationCanonicalizerContractTest` 3 条钉死（错字纠正/真实地名不互串/三处比较全走纠错）。

**教训**：识别错字的第一反应应该是「**我们有没有已经在用的纠错字典**」，而不是发明一个新的宽松匹配。封闭字典的纠错自带"以上都不是/它是别的真地方"的答案，通用容错没有。

**症状**：某段前置处理"代码明明写了、也测过"，实机却从不执行，日志里连它的探测行都没有。

**现场记录（追加）**

## E39 分类判据不具排他性：两类东西共享同一种像素证据 → 高置信地判成另一类

**症状**：分类器带着"高分"给出笃定的错误结论（`green=207 result=true`），下游按错误类别执行或落空；而且历史上"一直没出事"，让人误以为判据是对的。

**机制**：判据数的是**两类都有**的证据（绿像素既出现在选项行、也出现在正文内联链接里），只靠阈值和几何边界侥幸区分。任何几何/内容漂移（带子上移 8px、正文链接恰好落带内）立即翻车。**历史考古确认**：`hasOptionInLowerHalf` 自最早提交起就是"下带绿像素>150"，从未有过排他性判据；`findGreenTextBands` 只用于确认选项框后挑行，从未参与类型判定。

**实例（2026-08-01 20:23 天庭暗雷）**：到图 STORY 面板正文里的地名链接「御马监」落在选项带（未提交的 34px 裁切带比基线 42 上移 8px），绿 207>150 → 判 OPTION → 到图清理的 STORY 分支不触发。取证：`images/temp/..._option_lower_34_green.png` 逐行数——字形行 0-11 每行 7-20 绿(链接字)，row14 一条 47px 实心横线(下划线)，34 带合计 207、基线 42 带只剩 106。**错误的修法（已撤回）**：把 OPTION 也交给 closeObservedDialog——其关键词失配回落 `clickGreenOption` 会去点链接开导航，比不清更糟。

**修法**：找**只属于一类**的证据。选项行是绿字**独占成行**；正文链接与白色剧情字**共享同一批行**。`measureOptionRows`：对每条绿带在其行范围内复测绿/细白，`白*2 ≥ 绿` 判为正文绿（proseGreen），不计入选项证据；合格绿过阈值才是 OPTION，多行判定也只数合格带（链接的字形带+下划线带曾以 2 条原始带触发多行误判）。合同 `DialogOptionRowProseDiscriminationContractTest`（3 条，真实 OpenCV 管线跑合成图）。

**判据**：写 `count(某特征) > 阈值` 的分类时，问一句**这个特征是否只有目标类才有**——答案是"别的类也有，只是通常少一点"，就必须再找一个排他维度（共行白字、下划线形态、独占性），否则就是在赌阈值。误判发生时先取证 debug 掩膜逐行数像素，再动分类器；**不许**在下游用"两类都处理"来掩盖分类错误（那会把错误分类的动作真的执行掉）。

## E40 暂停/恢复后双方对同一 startRequestId 的生命周期语义不同步 → 已跑过轮次的任务被云端按"启动前预检"终止为 SKIPPED

**症状**：暂停再恢复后任务表面继续正常跑，若干秒到几分钟后突然拿到终态 `SKIPPED`，客户端按失败清场，窗口原地站住。metrics 里明明有 round SUCCESS。

**机制**：`SKIPPED` 在 `CloudTurnTaskRuntime` 里唯一的产地是 `aggregate` 初值 + role preflight `materializeAssignedEntry==null` 全跳过——语义上**只应出现在任务一次都没执行过的启动前**。暂停(`Remote start lifecycle invalidated: reason=pause`)后恢复复用**同一个 startRequestId**：客户端认为旧 run 还活着继续跑轮次，云端却把这次 start 当新启动重走角色预检；窗口 `role=UNKNOWN` → 物化不出有效任务 → 终态 SKIPPED 下发到还在跑第 2 轮的客户端。

**实例（2026-08-03 07:09，67555 修罗队长，另一 agent 定位/本 agent 复核）**：07:08:20 Ctrl+Shift+F11 暂停、07:08:50 恢复（同 id 2bf3b727），round-1 07:09:35 SUCCESS、round-2 已启动，07:10:37 云端 SKIPPED → 清场站住。62 秒间观察面 135 次上报零故障，云端进程活着——不是挂死。（云端侧那条 `role preflight produced no effective task` 原始日志被 07:11 重启截断——已修 restart 脚本先归档再启动。）

**修法（P1，待实施）**：①已 ACK 且执行过 ≥1 轮的 run，云端禁止再走 role preflight、禁止产出 SKIPPED；②云端若确实丢失运行实例，返回显式"run-lost/需重启"错误而非伪装成业务终态；③暂停/恢复必须恢复**同一个**云端 task run，不允许客户端续旧 run、云端按新启动处理的分叉。

**判据**：任何"同一 id 二次到达"的接口，问一句**双方对'这个 id 现在处于什么阶段'的判断源是否同一份状态**——客户端凭本地续跑、云端凭重建预检，就是本错误。终态枚举里每个值都要有"允许出现的最晚阶段"，跨阶段出现即生命周期错误（SKIPPED 的最晚阶段=首个任务执行前）。

## E38 处理分支只认一种分类结果，真实场景落在另一种上 → 探测跑了、日志有、动作零

**症状**：修好"没被调用"之后，探测行终于出现在日志里，可后果一点没变——现场还是老样子。**探测有日志、动作没日志**，一眼看去像修好了。

**机制**：探测返回的是一个**分类**（类型、状态、枚举），而处理只写了 `if (x == 某一种)`。真实场景常年落在另一种上，`if` 不成立就静默走完，没有 else、没有 warn，只留下那行"我探测过了"。这是 E36 的下一层：E36 是**探测本身没跑**，本条是**探测跑了但结果没人接**。

**实例（2026-08-01 20:23 天庭暗雷）**：到图清框改挂到进分支后确实跑了，日志四次全是 `arrival-dialog result=OPTION`，而代码只接 `DialogType.STORY` → 一次都没清，右键继续打在框上。原因：到图弹的是 `使用引妖香`，绿选项行让 `hasOptionInLowerHalf`（`green=207 > 150`）判成 OPTION，而写代码时想当然认为"到图提示 = 剧情框"。

**修法**：STORY 与 OPTION 都清，交给既有的 `closeObservedDialog` 按形状分派——STORY 走基线故事点击，OPTION 走 `取消/离开/算了` 关键词关闭。**关键：OPTION 不能用"点第一个选项"来清**，那会替玩家把引妖香用掉；"清掉"和"作答"是两件事。合同 `TiantingDarkThunderArrivalDialogContractTest#bothDialogShapesAreCleared`（含禁止 `fallbackFirstOption` 的断言）。

**判据**：任何 `if (探测结果 == 某常量)` 的处理，问两句——**这个探测一共会返回哪几种？剩下那几种走哪条路？** 剩下的路是"什么都不做且不打日志"，就是本错误。分类型探测的处理要么穷举、要么在 else 里留一行 warn，绝不允许静默落空。

## E35 等待预算到期后"放行"——把"没等到"当"等到了"，带病继续

**症状**：本该人齐才走的流程带着残队推进；日志里等待的开始和结束都有，且"结束"看起来像正常继续。

**机制**：等待 API 给自己设了预算（如 120s），预算烧完后不是失败、不是上报，而是**返回和"等到了"同一个值并放行**（`return signal still present after 120000 ms, let task-specific flow continue`）。调用方拿到 true 分不清"信号消失"和"超时放弃"，于是把"没等到"当"等到了"。E16 的镜像：E16 是没有预算的无限重试，本条是**有预算但到期 fail-open**。

**实例（2026-08-01 13:52 天庭）**：战斗中两名队员死亡离场，队长战后 `waitForMembersReturnIfNeeded` 看见归队信号、等满 120s、放行 → 带 3 人开下一条腿，37 回合残队苦战；同型的回城前等待会把没归队的队员整轮丢在野外。对照抓鬼的门：`team return signal still present and under-five is disabled; yield for members`——信号不消失就一直 yield，**人不齐不走**。

**修法**：天庭战后与回城前两处等待改为循环窗口——`waitForMembersReturnIfNeeded` 返回 true 且 `isReturnTeamSignalPresent()` 仍在 → 再等一窗，带 stop 检查；信号消失才前进。（服务 API 本身"超时与成功同返回值"的缺陷保留原样未动，调用方用第二个探测区分。）

**判据**：任何"等待 X，最多 Y 秒"的调用，问一句**Y 秒到了还没等到时，代码走哪条路**——如果和"等到了"走同一条路，就是本错误。fail-open 只允许用在"继续也无害"的场合，人数、前置条件、安全闸都必须 fail-closed。

## E33 匹配返回的是中心点，调用方当成左上角又加了半个模板 → 点到隔壁那一行

**症状**：模板匹配得分 1.0、日志一切正常，但点击没有产生预期结果，甚至触发了**相邻选项的破坏性动作**。表面看像"模板匹配不准"或"对话框位置漂移"，实际匹配完全正确，错的是最后一步坐标换算。

**根因**：`ImageFinder.find` 返回的是匹配区域的**中心**，不是 OpenCV 原生的左上角——
```java
double centerX = mmr.maxLoc.x + target.cols() / 2.0;
double centerY = mmr.maxLoc.y + target.rows() / 2.0;
```
调用方把它命名为 `topLeft` 并再加一次 `width/2, height/2`，于是点击点被推到"中心 + 半个模板"，即模板的**右下角**。文字选项高度只有 14px、行距 17px，半个模板（+9px）刚好把点推过行边界。

**实例（2026-07-31 抓鬼接任务）**：`accept.png`(61x18) 匹配「我来帮你」得分 1.0，真实中心窗口相对 (297,434)；`clickTemplateCenter` 却点了 (327,443)（日志 `source=queued:catch-ghost:accept x=1728 y=605`）。实测行位置：第 1 行「我来帮你」y=427..440，第 2 行「**我要取消全队任务**」y=444..457。y=443 落在行间空隙最后 1 像素，而游戏选项热区是**行框**（含字上方行距）→ 归属第 2 行 → 每次接任务都在取消全队任务，随后云端走 cancel 恢复流程重试，无限循环。`JianghuLilianDialogLocalOperation` 的 accept-normal / accept-reset 有完全相同的写法。

**判据**：点击坐标与匹配坐标相差**恰好半个模板**（本例 +30,+9 对 61x18）→ 一定是坐标系用反了，不是匹配漂移。反证：同仓的 `DialogService`、`TurnMatchStepExecutor` 都是 `candidate - template.getWidth()/2` **减**半个模板来还原左上角——全仓约定就是"返回值是中心"，只有这两个对话框类反了。

**修法**：`clickTemplateCentre(source, centre)` 直接点返回值，参数名从 `topLeft` 改为 `centre`，不再传模板尺寸（传了就有人想加）。

**教训**：跨函数传坐标时，**参数名就是契约**。`Point` 不带语义，一个叫 `topLeft` 的变量装着中心点，静态检查、类型系统、code review 全都拦不住，只有实机点错才暴露。新写"匹配→点击"这一步时，先回答一句：**我拿到的这个点，是角还是心？** 拿不准就去看返回它的那个函数最后一行加没加 `/2`。

## E34 用一种按键的动作反复打在只认另一种按键的控件上 → 动作全发出去了，目标毫无反应

**症状**：日志里 `MOVE_MOUSE` + `CLICK_*` 一枪不落地发，鼠标肉眼可见移到了目标上，就是"点不下去"。像是坐标差一点点（对照 E33 会先怀疑坐标），实际坐标没问题——**按键类型不对**，或者压根没人负责点这个控件。

**根因**：某个宏/巡逻循环固化成一种输入（这里是 `WildBattleTask.clickBundle` = `MOVE_MOUSE` + `CLICK_RIGHT` 走位），而流程中途会出现一个只响应**另一种**输入的控件（选项对话框的链接只认左键）。循环对这个控件没有任何认知，于是一直用自己那一种按键"打过去"，外部看是卡死。

**实例（2026-07-31 抓鬼暗雷）**：队长 `hwnd-3AB11B6` 17:20:47 点绿链→判为暗雷；17:21:18.149 云端主动清掉对话框兴趣，理由写死 `catch-ghost dark-thunder has no kanda dialog`；17:21:19 起进入四点巡逻，`patrol click submitted` index 20/21/22… 全是 `CLICK_RIGHT`。从 17:20:47 到用户急停（17:21:57）**这个窗口一次左键都没有**。用户实机看到的"鼠标到了链接上、点了、链接没动"就是这些右键。真实业务是：巡逻打到暗雷会弹一个**验证选项框，点第一条链接才进战斗**——流程文档里根本没有这一种中途状态，所以代码里也没有。

**判据**：三问连答——①这一段循环发的是哪种按键？②这段时间屏幕上可能出现哪些控件？③其中有没有只认另一种按键的？只要存在，循环里就必须有一步显式地"看一眼 + 用对的按键处理"。另一个强信号：**代码里有一句主动关掉观察/兴趣的话，理由是"这里没有 X 对话框"**——这种断言几乎总是只对主线成立，漏掉了中途弹出的那一类。

**修法**：循环每一拍在发下一枪之前先做一次**纯当前屏**探测（`detectDialogTypeNoFocus(..., waitBeforeCaptureMs=0)`，别用默认那个白等 700ms 的重载），命中就走已有的对话框处理（本例复用天庭 `DialogHandleRequest.fallbackFirstOption`，不新造），处理成功这一拍不再发原来的按键、直接 park 等后续事实；探测不到/处理失败都不算失败，下一拍再看（否则踩 E24）。合同要钉死"什么时候看、点哪一条、点完等什么"，并单独钉一条"这个循环的 bundle 里没有左键"，把因果写进测试。

**教训**：**动作发出去 ≠ 目标收到**。日志只能证明"我按了"，证明不了"它认"。排"点了没反应"时，先确认按键类型对不对，再去怀疑坐标。

**第三形态（2026-08-01 天庭引妖，用户指出）：巡逻的右键落在 story 框上**。暗雷到图后弹「引妖」story
消息，四点巡逻的右键点在框上而不是地面——右键关不了 story 框，角色不动、turn 照报 COMPLETED，巡逻空转。
**位置由用户拍板**：这个 story 只在到达时弹、点一次就没，所以清理是**一次性的**，放在"停稳 + 确认暗雷 +
即将做本分支第一次屏幕探测（读飞行状态）之前"——天庭 `DETECT_FLYING`、抓鬼/新手 `darkThunderFlying==null`
读取前各清一次；**严禁放进巡逻循环每拍截屏**（第一版就是这么写的，被用户否掉：点一次就没的东西不配每拍
检测）。巡逻循环里保留的只有抓鬼/新手的**选项验证框**检查——那个确实是巡逻中途随时会弹的。
合同 `CatchGhostDarkThunderPatrolDialogContractTest` 8 条：story 不归巡逻检查管（不点第一条、不做清理）。
**判据同 E34 主条**，外加一条节奏纪律：**中途处理的频率要配事件的出现模式**——只出现一次的事件配一次性
清理点，随时会弹的事件才配循环内检查。

**姊妹形态（2026-08-01 天庭回城）：一次性的清理遇上多页的东西**。`CloudUiCleanerPort.closeSafeDialogInCloud`
对故事框只点**一次**，而天庭「已成功捉拿妖王，打开任务物品栏使用天庭焰光旗…」是**两页**：回城后的
`round-done-cleanup` 点掉第一页就返回，第二页留在屏幕上挡住李靖；下一轮 `NPC smart click first attempt
failed`，靠 accept 重试里的第二次 `cleanUpAll` 才点掉第二页。用户看到的是"回城清理好像没做"，实际做了、
只是没做完。日志形态：连续两条 `dialog handle result: ... type=STORY status=STORY_CLICKED`，中间夹着一次
失败的 NPC 点击。→ 故事框改为**点到 inspect 报 NO_DIALOG 为止**（上限 4 次）；选项框保持只答一次——
回答选项是一次业务决策，清理不许反复替用户按。合同 `CloudUiCleanerStoryPagesContractTest`（4 条）。
**判据**：凡是名字里带"全部/all/清空"的收尾动作，问一句**它面对的东西可能不止一个/不止一页吗**；
是就必须循环到"看不见了"，而不是做一次就宣布干净。

**根因**：迁移代码把三态事实 `PRESENT / ABSENT / UNKNOWN` 压成布尔值。timeout、stale action、binding
未就绪和 observation 尚未返回都属于 `UNKNOWN`，却被当成 `ABSENT`。该 dirty hunk 同时绕过受保护基线
`696a12b0`、CR188/CR229 的 title-first 热启动规则和 TURN-40E 的“stale 等 Runner refresh，phase 不下沉”。

**规则**：任何业务 phase 只能由 exact positive/negative 事实推进；等待到期、没有事件、旧事实、传输未知或
binding 未建立不得合成 negative。五环尤其固定为 title-first：prepared/title positive 接管已有任务，exact fresh
`TASK_NOT_FOUND` 才能接任务，其余状态留在 `HANDOVER_DETECT` 并等待 Runner refresh。迁移前后必须逐方法对照
权威基线；发现差异而没有用户明确批准时，按回归做最小恢复，不得用 magic timeout 修补。

**2026-08-06 G044 补充：** “exact task-run”只证明事实属于同一次运行，不证明它仍是当前画面。ready facts 无 TTL
时，接任务前的 `TASK_NOT_FOUND` 可以在接任务成功后继续留在同一 slot。消费 negative 前必须比较同 slot 的单调
sequence；若其后已经出现任何 PreparedAction，旧 negative 已被更新观察 supersede，只能回到 UNKNOWN 等新事实，
不得重复累计同一 negative。普通 STORY 明确存在但模板 miss 也不是“没有结果”：应发布 typed miss action，由任务在
非战斗时关闭遮挡后重读 tracker；战斗中不得为推进 tracker 点击 Story。

## E46 已消费 action 的本地 marker 没有绑定 interest 代次，阻断下一段 dialog 链

**现场**：2026-08-06 `23:12` 全停重跑五环。启动屏幕 `INSPECT` prepared action 已被消费，云游大师也已真实
点击；Client 随后为新的 `accept-dialog:nearbyAcceptNpcPathing` interest 上报 `dialog present`，Cloud 却没有创建
新的 `wuhuan-dialog` FrameDemand，主任务持续等待 `PREPARED_ACTION_READY`。

**根因**：observer 只保存 `wuhuanDialogAwaitingActionId` 与旧 presence sequence，不保存产生该 action 的
`interestId`。prepared slot 清空后，只要当前存在任何 active interest，旧 marker 就不会进入 title rearm、也不会退休；
新的 interest 因此被 `awaitingActionId != null` 永久挡住。

**规则**：跨 interest 的一次性 demand/action marker 必须绑定 originating `interestId`。bound slot 仍存在时保持互斥；
slot 已消费且当前 active interest 已换代时，旧 marker 必须只退休，禁止把旧 action 的 rearm 套到新 interest，也禁止
让旧 marker 阻挡新的 `presence -> FrameDemand -> action`。同一 interest 的重复帧仍按既有 ACK/rearm 合同处理。
