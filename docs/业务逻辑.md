本章记录当前版本与后续高级版之间的本地队伍设计边界。它不是当前修复卡，也不是现阶段必须实现的功能；它用于避免后续设计时误把“后加窗口”“多队长”“动态加入队伍”混在一起。

## 当前初级版边界

1. 当前版本按一组五开设计：
   - 一个本地队长；
   - 最多四个本地队员；
   - 同一批 UI 启动形成一个本地队伍 session。

2. 本地队伍 session 只在“同批启动”时生成。  
   启动后再注册或打开的新窗口，不会自动加入已经运行中的本地队伍 session。

3. 当前的“同组”判断是本地控制层概念，不是游戏内队伍 ID：
   - 同批启动的窗口共享同一个 `localTeamSessionKey`；
   - runner live role preflight 识别其中哪个窗口是队长；
   - 队长按这个 session 打开 `TEAM_RETURN`、`FIRST_AID`、`COMMON_BOX` 等 capability；
   - 队员只消费同一个 session 里的 capability。

4. 当前初级版不支持运行中动态扩容本地队伍。  
   如果中途新加一个号并单独启动自动挂机或任务队列，它默认是 standalone/独立上下文，不属于当前队长 session。

## 后加窗口的已知风险

1. 后加窗口如果不属于当前本地队伍 session，就不知道当前队长是谁。

2. 后加窗口不会等待当前队长打开的本地 capability。  
   它不会自然遵守当前队长的 `TEAM_RETURN`、`FIRST_AID`、`COMMON_BOX` 放权节奏。

3. 后加窗口通常不会点错到队长窗口，因为真实输入仍绑定自己的 hwnd。  
   但它可能抢全局 task turn / input queue 的时段，让前台焦点切到自己窗口，从而打断或延迟当前队长的关键动作。

4. 因此当前操作约束是：本地队伍正在运行时，不要把后加窗口直接作为普通 standalone 自动挂机号启动，除非明确接受它会与当前队伍竞争全局输入时段。

## 后续高级版方向

1. 第一优先级不是“自动动态加入队伍”，而是“后加 standalone 窗口让着正在运行的本地队伍”。  
   设计方向可以是：当本机存在 active local-team leader 时，未入 session 的 standalone 自动挂机窗口进入隔离/让权模式。

2. 隔离/让权模式的候选规则：
   - 可以后台观察自身战斗状态、血蓝状态和必要诊断；
   - 不主动抢 task turn 做补血、三技能、左上角状态、盒子、归队等前台动作；
   - 只有当没有 active local-team leader，或用户显式允许“独立抢输入”，才允许 standalone 维护抢前台。

3. 如果未来需要真正支持运行中补号，应做成显式手动 attach，而不是自动猜测：
   - 用户明确选择“加入当前本地队伍支援”；
   - attach 只能在安全点生效；
   - attach 后该窗口先进入只等 capability 的支援 worker 状态；
   - 必须记录 attach 到哪个 session、attach 时间、窗口身份、是否允许前台动作；
   - 不应在没有明确用户动作和日志证据的情况下自动把陌生窗口纳入当前队伍。

4. 如果未来高级版支持两个或多个队长，应把它设计成多个独立 local-team session：
   - 每个队长和自己的队员共享各自 session；
   - capability 必须按 session 隔离；
   - A 队长打开的 `TEAM_RETURN` 不能被 B 队员消费；
   - 物理输入仍然全局串行，但后续可以引入 session/leader-aware priority，而不是只靠公平锁排队。

## 当前不做的事

1. 不在初级版实现运行中自动动态加人。

2. 不自动判断游戏内队伍 ID 或猜测哪个新窗口属于哪个队长。

3. 不把后加 standalone 窗口默认接入已有 local-team session。

4. 不把这个设计备忘混入修罗、五倍、盒子、回程或补给的现有业务验收；如需实现，应另开专门 CR。

# 独立自动战斗 Runner 战斗与补给规则

## [BR-AUTOBATTLE-001] 战中只维护面板，Runner 脱战后才补给

1. 用户直接启动的独立自动战斗以当前 exact window/task-run 的 Client Runner 战斗边沿为唯一战斗权威，
   不再由 Cloud command-plane battle radar 另行覆盖战斗状态。
2. Runner 报告 `IN_COMBAT` 时，只允许维护自动战斗面板；禁止执行人物或宝宝 HP/MP 补给。
3. Runner 报告 `NOT_IN_COMBAT` 后，即时恢复路径先固定等待 `1500ms` 让场景和右上角状态条稳定，并记录
   `configuredMs` 与实际 `elapsedMs`；随后才执行既有 `FULL_RECOVERY`，按当前运行配置检查并补充人物/宝宝血法。
   已经延后到回城后才消费的 `CLIENT_RUNNER_EXIT` 恢复不重复等待。
4. 若旧脱战事件已被更新的入战事实覆盖，禁止补给；若旧入战事件已被更新的脱战事实覆盖，禁止补做面板输入。
5. Client 因 `LOCAL_COMBAT_ACTIVE` 或其他原因拒绝补给输入时，本轮补给额度不得视为已消费；下一次 exact
   脱战仍应重新检查。健康帧或确认没有目标可以正常消费本轮检查。
6. 该规则不改变补给阈值、状态条坐标、`Alt+8` 刷新周期、Client 战斗输入安全门或本地队员支援逻辑。

## [BR-WILDBATTLE-001] 野外战斗按下一战斗轮次预约全队补给

1. 野外战斗的队长 exact Runner 战斗边沿是同一本地队伍的唯一战斗节拍。队长 `IN_COMBAT` / `NOT_IN_COMBAT`
   必须通过既有同组广播送达有效任务为 `AUTO_BATTLE` 的队员；队员不恢复独立战斗采样。战中每个窗口仍只维护
   自己的自动战斗面板。
2. 第 N 轮脱战后，每个 exact window 都可用既有 no-focus HP/MP 探针检查自身补给需求。需要补给时，只登记到
   第 N+1 轮的队伍补给预约；第 N 轮不立即抢输入，也不要求队长为没有预约的轮次打开维护窗口。
3. 第 N+1 轮战斗期间，队长读取同组预约快照。第 N+1 轮脱战后，只有快照中存在到期预约时，队长才打开
   `FIRST_AID` capability 并放权；预约窗口按既有共享 task turn 串行执行缓存补给计划。全部到期预约完成或维护
   窗口达到有界期限后，队长关闭 capability 并继续四点巡逻。
4. 队长也是普通补给参与者：它在第 N 轮登记的需求必须在第 N+1 轮维护窗口中执行，不能因为它负责开窗而跳过。
5. 同一窗口如果在第 N+1 轮已经实际完成过人物或宝宝补给，第 N+1 轮脱战后的登记步骤必须跳过一次，禁止在
   补给前的旧血蓝画面上连续预约第 N+2 轮。未实际执行、输入失败或探针 `UNKNOWN` 不得记为已补给。
6. 预约、到期与已补给标记必须按本地队伍 session、exact window 和战斗 generation 隔离；停止/新任务运行时清理，
   不得跨队、跨窗口、跨旧 run 继承。

# [BR-COMMON-BOX-001] 通用盒子优先消费与30秒生命周期

本文里的“盒子”指游戏窗口右下区域可由模板识别并点击的临时目标。该逻辑是通用业务能力，首批接入修罗和五倍；后续其他主任务如果有同样需求，也应复用同一套检测、pending、消费和过期规则，不各自复制一套私有流程。

## UI 开关

1. `队长要盒子`：
   - 默认勾选；
   - 只控制队长窗口是否检测和点击盒子；
   - 关闭后，队长不检测、不消费，并清掉队长窗口自己的 pending 盒子标记。

2. `队员要盒子`：
   - 默认不勾选；
   - 只控制队员窗口是否检测和点击盒子；
   - 关闭后，队员不检测、不消费，并清掉队员窗口自己的 pending 盒子标记。

3. 两个开关互不影响：
   - 勾选 `队员要盒子` 不会让队长跳过盒子；
   - 队长是否要盒子只看 `队长要盒子`；
   - 队员是否要盒子只看 `队员要盒子`；
   - 两个都勾选时，队长和队员都可以各自检测、各自点击；
   - 两个都不勾选时，全队都不处理盒子。

## 识别区域和模板

1. 盒子识别使用窗口相对 ROI，不写死桌面绝对坐标。  
   用户给出的样本绝对坐标是左上角 `1997,636`、右下角 `2056,664`，样本队长窗口左上角是 `1374,46`，所以对应窗口相对 ROI 为：
   - 左上角：`623,590`；
   - 右下角：`682,618`；
   - 大小约 `59 x 28`。

2. 模板放在 `images/template/common/` 下，使用通用命名。  
   推荐名称：`leader_box_marker.png`。  
   虽然名字里可以保留 leader 语义，但业务规则必须按通用盒子处理：队长和队员都可以复用同一个模板。

## 队长检测和消费

1. 队长只在 `队长要盒子` 开启时处理盒子。

2. 检测时机：任务完成后，队长确认已经回程以后。  
   回程确认后，后台截取当前绑定队长窗口的盒子 ROI，并做模板匹配。这个后台识别不能阻塞队长继续领下一轮任务。

3. 检测成功后，不在尚未完成回城/归队收尾的中途点击。
   当前队长窗口记录一个 pending 盒子标记，至少包含：
   - windowId / 当前窗口绑定；
   - 匹配时间；
   - 过期时间；
   - 模板匹配点和最终点击点；
   - 来源任务，例如修罗或五倍。

4. 队长消费时机：本轮成功且归队门完成后、记录完成进度与任何轮间随机等待之前。
   队长先检查自己的 pending 盒子标记；如果存在且未过期，就优先点击识别到的 template 位置。点击成功后清掉 pending 标记，然后才允许进入 G185 轮间休息或结束任务。该消费不受“是否还有下一轮”限制，因此最后一轮也必须尝试；不得继续拖到下一轮接完任务或导航开始以后。无 pending、开关关闭、已过期或未匹配时按公共服务既有结果继续，不新增私有重试。

5. 队长 pending 生命周期为 30 秒。  
   从后台识别成功并记录 pending 的时间开始计时；超过 30 秒仍未消费就丢弃，不能跨很久再点。

## 队员检测和消费

1. 队员只在 `队员要盒子` 开启时处理盒子。

2. 检测时机：队员战斗结束以后。  
   每个队员窗口在战斗结束后后台截取自己的盒子 ROI，并做模板匹配。队员之间的 pending 标记互相独立，不能共用、不能串窗口。

3. 检测成功后，不立刻抢输入。  
   当前队员窗口记录自己的 pending 盒子标记，字段和队长 pending 一致。

4. 队员消费时机按本地队伍归属区分：
   - standalone 队员：自己的 pending 存在且未过期时，在下一次可用 input opportunity 尽快先点击；
   - 已确认跟随本地队长的队员：保留自己的 pending，等队长释放 task turn、该队员实际拿到 task turn 后才点击，不能抢队长输入。
   点击后清掉自己的 pending。

5. 队员 pending 生命周期同样为 30 秒。  
   从后台识别成功并记录 pending 的时间开始计时；超过 30 秒仍未消费就丢弃。

## 优先级

1. 只要当前窗口有未过期 pending 盒子，盒子点击就是当前窗口最高优先级维护动作。

2. 盒子消费优先于：
   - 队长加血；
   - 队员加血；
   - 三技能；
   - 摄妖香 / 14 号箱；
   - 医宝宝；
   - 修装备；
   - 其他 opportunistic maintenance。

3. 原因：盒子 pending 只有 30 秒生命周期，不能被加血、三技能、摄妖香、医宝宝、修装备等维护动作拖到过期。

## 适用任务

1. 修罗和五倍都要接入这套通用盒子逻辑。

2. 修罗队长：回程确认后检测；下一轮点接任务 NPC 前消费。

3. 五倍队长：按同样的业务点接入，任务完成并回程确认后检测；本轮成功且归队完成后、进度记录和随机休息前消费。

# Expected 战斗快脱战与回程验证兜底

> **业务基线使用规则（五倍 / 修罗）：** 本文的已确认规则与其中标注的迁移前本地基线，是后续
> 云端化、Runner、调度或性能 CR 的默认业务裁决依据。若 CR 没有得到用户明确批准去改变业务逻辑，
> 必须按基线等价迁移；不得自行新增 TTL、二次验证、park/yield、重试、cleanup、fail-closed 或改变
> phase/fallback 顺序。每张卡交付时必须写明核对了本文哪一条规则；没有已批准业务差异时，固定记录
> `无已批准业务差异；按基线等价迁移`。
>
> **选择性变更门禁：** 一张 CR 只批准其明确写出的目标，不代表 agent 可以自行决定任何会改变基线
> 判断、条件、phase 转移、优先级、fallback、时序/过期或输入/验证顺序的实现方案。只要完成 CR 存在
> 这种选择，agent 必须先把选项、受影响的基线规则、运行影响和推荐写回 CR 卡并向用户请示；用户未明确
> 选择前不得编码。`完成 CR`、`修好问题` 等泛化指令不构成业务逻辑变更授权。

本文里的 `expected 战斗` 指任务自己确认触发的战斗，例如修罗通过 `看打` / tracker shortcut 确认进入的战斗，或五倍正常目标链路确认进入的战斗。`unexpected / incidental 战斗` 不适用本章，仍按原有保守战斗恢复逻辑处理。

## 总原则

1. 快脱战探针只用于抢跑，不作为最终业务事实。

2. Runner / battle radar 的完整战斗状态仍是可信兜底，但不应该在每次回程前额外阻塞一次快路径。

3. 对 expected 战斗，第一层可信业务证据是“回程道具是否把角色送回起点地图”：
   - 回程道具使用后验证到起点地图，说明本次快脱战可被接受，继续正常回程后流程；
   - 回程道具使用后没有验证到起点地图，说明本次快脱战不可信，不能继续当作正常脱战处理。

4. 因此不要在回程前增加额外 Runner/full-radar 确认。  
   回程前确认会把快路径重新拖慢，而且不是必要条件。

## 已验证回城快照（五倍、修罗共用）

1. 五倍或修罗使用对应回程道具，且已由当前位置验证回到各自起始城后，`起始地图 + 坐标` 是本轮后续
   接任务的**任务事实**，不是 3 秒或任意 TTL 的短暂位置缓存。

2. 下一次接任务 NPC 导航必须复用这份快照，不能因为队伍归队、云端命令、重试、排队或日志处理经过了几秒，
   又重复打开小地图/重读地图位置来“确认”。回城坐标不在 NPC 直点半径内时，仍按原有导航去 NPC；本规则
   只禁止重复确认，不改变近点直点与远点导航的业务分流。

3. 快照只在**新的接任务 option 已实际点击成功**后清除。NPC 点击、dialog 准备、模板 miss、云端 fallback、
   归队等待、导航重试和任务暂停恢复都不能清除它；接任务未成功时必须继续保留。

4. 本规则同时适用于五倍和修罗。任何后续迁移不得把已验证回城重新降级成带时间过期的 observation cache，
   也不得为该路径新增第二次地图/位置验证。

## 回程验证失败后的兜底

1. expected 战斗快脱战后，任务可以立即进入回程道具流程。

2. 如果回程道具没有使用成功，或使用后没有验证到任务起点地图，必须先进入“快脱战失败兜底”判断，不能直接继续清 UI、导航回起点、重接任务或宣告任务失败。

3. 兜底判断必须让 Runner / battle radar 做可信状态纠正：
   - 如果可信状态确认当前仍在战斗中，则本次快脱战视为 false positive；
   - 任务状态必须回到对应的战斗等待阶段，例如修罗 `WAIT_COMBAT`、五倍 `WAIT_BATTLE_FINISH`；
   - 已挂起的 fast expected exit 后置恢复（人物/宝宝血法、摄妖香等）不能在仍在战斗时被消费；
   - 后续继续等待真正脱战。

4. 如果 Runner / battle radar 也确认当前不在战斗，但回程仍未验证到起点地图，则按原有“回程失败 / 道具失败 / 安全恢复”逻辑处理。

5. 这个兜底是修罗和五倍的通用规则。  
   只要任务使用 `FAST_EXPECTED_EXIT` 或等价的 expected 战斗快脱战策略，就必须在回程验证失败后接入同一套纠正逻辑。

## 不改变的边界

1. 不改变快脱战探针本身的 ROI、阈值、延迟和 1 秒 cadence。

2. 不改变 expected 战斗正常回程成功路径：成功回到起点地图后仍然按现有任务流程继续。

3. 不改变 unexpected / incidental 战斗恢复策略。

4. 不新增回程前等待，不让每一轮都多付一次完整 Runner/full-radar 确认成本。

# 修罗与五倍普通怪共用：入战识别、云端 fallback 与失败上限

本章是修罗与五倍**普通怪**从点击左侧 tracker 绿链到真实进入战斗之间的共同业务合同。它覆盖两者此前
“停下后立即由前台重复点绿链”的处理；黄袍怪连战、白龙马/显形镜、暗雷怪不自动适用，仍以各自章节为准。

## 共用主链

1. 队长成功点击本轮左侧 tracker 绿链后，记录本轮及本次绿链尝试的 `attemptId`，然后放权等待。

2. 本地 Runner 在该任务既定的时间闸门到达后，持续进行本地入战模板的小 ROI 匹配。
   本地未命中只表示当前帧没有入战选项，不能唤醒队长、不能触发 fallback、不能停止或重置本地匹配。

3. 本地命中入战模板时，发布当前 `attemptId` 的入战 `prepared action`；前台消费它并点击对应选项。
   点击后由既有战斗状态确认链确认是否真实进入战斗。修罗已启用的本地 `kanda2` 直点例外也遵守同一
   确认规则：一次实际点击后连续等待四个 Runner 战斗采样；若仍没有 `IN_COMBAT`，同一 `attemptId`
   最多再实际点击两次。输入未实际执行不计次数。三次实际点击仍未进战时，本地只上报
   `ENTER_BATTLE_CLICK_FAILED`，不自行复按绿链。

4. 角色停稳时，后台为当前 `attemptId` 截取一张静态图并交云端识别。停稳本身不是失败，不代表需要点击
   绿链，也不停止本地模板匹配。

5. 云端在静态图中识别到入战选项时，下发带当前 `attemptId` 的 prepared action；前台按现有一次性消费规则
   点击，并把点击 outcome 回报云端。

6. 本地或云端任一条链路成功点击并确认真实进入战斗后，立刻停止本地匹配，并清理本轮 dialog interest、
   prepared action、静态图请求及 pending fallback。另一条链路的迟到结果必须丢弃。

## 唯一允许触发 fallback 的条件

1. 本地 Runner 无权触发 fallback；本地持续未命中、prepared action 尚未到达或本地结果迟到，均不是 fallback
   条件。

2. 只有云端针对**当前 `attemptId`** 得出以下任一结论，才可以下发 fallback：
   - 停稳静态图未识别到本任务的入战选项；
   - 云端曾下发入战坐标，前台实际点击后回报失败，云端确认该次点击未能进入战斗。
   - 修罗本地 `kanda2` 已实际点击三次、Runner 仍未确认 `IN_COMBAT`；这是点击确认失败事实，
     不是本地自行 fallback 的授权。

3. 前台收到当前尝试的云端 fallback 后，才复按本轮保存的左侧绿链点，使入战 dialog 有机会重新出现。
   复按开始下一次 `attemptId`，但**不停止本地持续模板匹配**。

4. 旧 `attemptId` 的静态图结果、云端 miss、坐标、点击 outcome 或 fallback 一律丢弃，不能跨尝试复按绿链。

5. 只有云端已下发 fallback、且前台确实实际执行了该次绿链复按，才记一次失败。累计三次有效云端
   fallback 后仍未进入战斗，放弃本轮并走该任务既有的放弃/恢复路径；不得无限复按。

## 任务间允许不同的内容

共同流程、尝试编号、云端权限、三次上限和“进战即停止本地匹配”的边界完全相同。唯一允许任务各自定义的是：

| 项目 | 修罗 | 五倍普通怪 |
| --- | --- | --- |
| 本地持续匹配模板 | 修罗 `kanda2` / 看打模板 | 五倍普通怪对应的本地入战模板 |
| 云端静态图识别语义 | 修罗“看打”对话选项及其坐标 | 普通怪入战对话选项及其坐标 |
| 前台最终点击 | 修罗“看打” | 普通怪实际进入战斗的对应选项 |

除以上模板、云端匹配语义和最终对话选项外，不允许五倍普通怪与修罗分别实现不同的停稳、fallback、复按、
失败计数或停止本地匹配规则。

- 修罗由 CR232 承接；当前旧的终态自动复按实现已被本章规则否定，待按本章修复。

   **2026-09-10用户追加批准删除地图开窗条件：** 目标地图名保留用于位置/路线诊断，不能再作为

   第一个绿字的 `targetMapName` 作为诊断信息，第二个 prompt 不保存第二份地图名。普通怪/黄袍第一战
   正常只有一个绿字目标地图名。

4. 同一窗口同一任务同一时刻只有一个当前 dialog interest。  
   注册新的业务 interest 会覆盖旧 interest。  
   这是运行时不变量，不需要在每个业务分支里重复写“先清旧的”。

## 需要清掉 interest 的业务边界

1. 每轮准备接五倍任务前清一次残留 interest。  
   这是进入新一轮任务前的兜底清理。  
   所以 `PRE_BATTLE_TIMEOUT`、回城、失败恢复到重新接任务路径时，不需要各自额外清一次；
   下一次接任务前会统一清。

2. Runner / 战斗守护发现当前窗口从“非战斗”变成“战斗中”时，清掉当前五倍 dialog 准备状态。  
   这里不区分 prepared action 点进去、意外进战斗、AutoCombat 观察到战斗。  
   只看状态事实：当前窗口已经进入战斗。  
   清理范围至少包括当前五倍 `dialogInterest`、`dialogPreparationRequest`、stale `preparedDialogAction`
   和对应 READY/prepare 状态；不能只清 `WUBEI_ENTER_BATTLE interest`，否则残留状态可能把 Runner
   在战斗中继续拉到 100ms/200ms/500ms dialog prepare 高频。

3. 白龙马 `WUBEI_PROBE_STORY interest` 的非入战结果需要清。  
   如果 Runner/provider 的显形镜结果是：
   - `wubei.probeWrongPosition`；
   - `wubei.probeStoryAbsent`；
   - `wubei.probeNoTarget`；
   
   队长消费这个结果后，清掉当前 `WUBEI_PROBE_STORY interest`，再去执行重新点当前绿字、
   同 probe 重试、切第二个 probe、或失败回接任务。  
   `wubei.probeTargetReady` 不作为额外手动清理点；它继续进入目标点击/入战链路，后续新的
   `WUBEI_ENTER_BATTLE interest` 或进入战斗状态会自然结束上一段业务等待。

## 不作为业务清理点

- 用户点击 UI 停止；
- 窗口 stop request；
- 异常导致当前 task run 退出；
- 程序关闭；
- 单轮回城；
- `PRE_BATTLE_TIMEOUT` 本身；
- 泛泛的 runtime reset / window reset。

这些可以作为实现层防御性清理，但不写成五倍业务逻辑验收要求。五倍业务只依赖上面的明确业务边界。

业务基线：以最近 push `origin/codex/migrate-runner-dialog` / `3f0a2e7` 为准。本地迁移改动不能额外改变白龙马业务判断。

## 到第一个显形镜前

1. 队长接完五倍任务。  
   状态：暂时通过。

2. [Phase: READ_TRACKER]  
   队长读取左侧任务追踪。

3. 如果任务追踪确认这是白龙马/显形镜 probe 任务，则初始化 probe runtime：
   - 保存当前任务追踪里的 probe 绿字链接；
   - `currentProbeIndex = 0`；
   - 当前目标是 `first-probe`。

4. [Phase: TRACKER_PATHING]  
   队长选择第一个绿字链接 `first-probe`。

5. 队长点击 `first-probe`。点击逻辑以 push commit `3f0a2e7` 为准，不新增到点前校验。

6. 点击完成后，设置 next phase 为 `RESOLVE_AFTER_PATHING`，然后队长立刻放权等待 Runner。

7. 🔔 Runner 观察移动。白龙马 probe 寻路等待只接受 Runner 的 `PATHING_TERMINAL` 门铃：
   - Runner 仍在观察移动时，只更新 `ACTIVE` 状态，不叫醒队长；
   - Runner 认为这一轮移动停下/终止时，发布 `PATHING_TERMINAL`。

8. 队长不应被 plain `STORY`、plain `OPTION` 或 plain `TASK_ATTENTION_REQUIRED` 唤醒。  
   状态：暂时通过。

9. [Phase: RESOLVE_AFTER_PATHING]  
   队长被 `PATHING_TERMINAL` 叫醒后，重新拿到 turn。

10. 白龙马 `first-probe` 不区分 `ARRIVED` / `STOPPED_AWAY`。  
    对这里来说，`PATHING_TERMINAL` 只表示“这轮移动停下来了”。

11. 不新增 hint gate。  
    不在使用显形镜前校验当前地图/坐标是否等于 hint。  
    原因是：如果位置不对，使用显形镜后，后续 `WUBEI_PROBE_STORY` 会识别“位置不对”。

12. 注册 `WUBEI_PROBE_STORY` interest。

13. 使用第一个显形镜。

14. 显形镜使用后，队长继续持有当前 task turn。  
    从这里开始，到本轮白龙马成功进入后续链路或失败回去重新接任务之前，白龙马后续热路径都不放权、不 park、不睡，也不让其他窗口/队员插队。  
    如果后续需要同一个 probe 再用一次显形镜，或短路径切到第二个 probe，也仍然按这个规则处理。

15. 删除队长侧旧的 `WUBEI_PROBE_STORY` 15 秒 / 80ms polling 兜底。  
    队长不再超时自造 `WHITE_TEMPLATE_NOT_FOUND`。  
    Runner/provider 必须给当前 `WUBEI_PROBE_STORY` 一个明确结果；没有 STORY 框时，统一返回
    `targetKeyword=wubei.probeStoryAbsent`、`matchedText=STORY_ABSENT`、`dialogType=NONE`、
    `clickRequired=false`。

16. 队长保持醒着，在当前 task turn 内等待 Runner/provider 给出 `WUBEI_PROBE_STORY` 的明确结果。  
    这里不释放 task turn，不进入 `park/yield`，也不依赖 `TASK_ATTENTION_REQUIRED` 门铃叫醒。  
    dialog 识别仍然完全由 Runner/provider 负责；队长只消费 Runner/provider 的结果。

17. 如果结果是 `wubei.probeStoryAbsent` / `STORY_ABSENT`，表示显形镜后没有 STORY 框。  
    当前 probe 可以再用一次显形镜；第二次仍然 absent，则本轮白龙马失败，回去重新接任务。

18. 使用显形镜后的四种业务结果。  
    显形镜之后，Runner/provider 必须返回明确业务结果；队长只消费这个结果，不自己读图、不自己猜。

    第一种：`wubei.probeTargetReady`。  
    来源：`3f0a2e7` 已有业务逻辑。  
    含义：当前 probe 使用显形镜以后，目标已经出现。  
    队长处理：标记当前 probe resolved，然后进入白龙马/目标点击逻辑。  
    约束：这里不能切第二个 probe，也不能回去重新点当前绿字。

    第二种：`wubei.probeWrongPosition`。  
    来源：`3f0a2e7` 已有业务逻辑。  
    含义：位置不对，或者显形镜用早了。  
    队长处理：回滚本次显形镜 attempt，保留当前 `currentProbeIndex`，回到
    `TRACKER_PATHING` 重新点当前这条绿字。  
    约束：这里不能切第二个 probe，因为第一个 probe 还没有被业务判废。

    第三种：`wubei.probeStoryAbsent`。  
    来源：CR39 用户批准的新逻辑。  
    含义：没有 STORY 框，画面上没有拿到可判断的显形镜结果。  
    队长处理：按第 17 点执行；当前 probe 第一次 absent 就同 probe 再用一次显形镜，
    同 probe 第二次仍 absent 就失败回去重新接任务。  
    约束：这里不做 tooltip fallback，也不切第二个 probe。

    第四种：`wubei.probeNoTarget`。  
    来源：CR40 用户批准的新逻辑。  
    含义：有 STORY，但两个白字模板都没有命中；业务上就是“这个 probe 点不是目标点”。  
    队长处理：标记当前 probe resolved。  
    如果还有第二个 probe，就切第二个 probe；如果没有第二个 probe，本轮失败，回去重新接任务。  
    约束：这里不再做 tooltip fallback。

19. 切到第二个 probe 的流程。  
    只有第一个 probe 得到 `wubei.probeNoTarget` 时，才切第二个 probe。

    队长处理：
    - `currentProbeIndex` 改成第二个 probe；
    - 点击第二条绿字；
    - 这段仍然属于白龙马热路径，队长继续持有当前 task turn；
    - 第二条绿字移动结束后，注册 `WUBEI_PROBE_STORY` interest；
    - 使用第二个显形镜；
    - 第二个显形镜以后，仍然按第 18 点同一套四种结果处理。

20. 目标出现后的点击逻辑。  
    来源：目标点击链路以 push `3f0a2e7` 为业务基线。  
    如果第一个或第二个 probe 返回 `wubei.probeTargetReady`，说明目标已经出现。

    队长处理：
    - 标记当前 probe resolved；
    - 调用 `tryClickProbeSpawnedTarget(..., storyConfirmed=true)`；
    - 这个函数先走 `tryClickTrackerCombatTargetSmart(...)`；
    - 普通智能点击失败或没有完成入战时，函数内部可以继续走 `3f0a2e7` 已有的
      direct-combat fallback；
    - direct-combat fallback 的入口是 `tryDirectCombatFromTrackerHint(...)`，里面才会使用
      Alt+A / 直接战斗点击模式；
    - 不新增点击算法，不改 tooltip / OCR / 模板阈值，不改目标坐标策略。

21. Tracker hint 策略。  
    来源：`3f0a2e7` 已有业务逻辑。  
    Tracker hint 来自前面点击任务追踪绿字后，从左侧任务追踪里解析出的目的地文本。  
    它记录到 `currentTrackerDestinationHint`，包含 `mapName`、`mapX`、`mapY` 和原始文本。

    队长点击白龙马/目标时，把这个 hint 填进 `NpcClickRequest`：
    - `mapName = hint.mapName()`；
    - `mapX = hint.x()`；
    - `mapY = hint.y()`；
    - `npcName = 白龙马`；
    - `targetRole = COMBAT_TARGET`；
    - `targetEvidence = CONFIRMED`；
    - `tooltipFirst = true`；
    - `expectedDialogTemplatePaths` 使用 `3f0a2e7` 的三个入战模板。

    业务含义：只在当前 tracker hint 附近，用白龙马目标名和 tooltip 优先策略去点目标，
    并用入战模板证明点对了。

22. 入战 prepared action 处理。  
    来源：`3f0a2e7` 已有业务逻辑。  
    `tryClickTrackerCombatTargetSmart(...)` 点完目标后，会调用
    `tryClickKnownEnterBattleDialog(...)` 消费 `WUBEI_ENTER_BATTLE` prepared action。

    队长处理：
    - 如果入战 prepared action 点击成功，`tryClickProbeSpawnedTarget(..., true)` 返回 true；
    - 白龙马流程进入 `WAIT_BATTLE_FINISH`；
    - 如果这条链路没有成功，则按 `3f0a2e7` 的函数返回逻辑处理；
    - 这里不新增“外层五分钟脱困”业务规则。

23. 进入战斗以后。  
    来源：`3f0a2e7` 已有业务逻辑。  
    如果成功进入 `WAIT_BATTLE_FINISH`，后面进入战斗等待/战斗结束逻辑。

    队长处理：
    - 进入 `WAIT_BATTLE_FINISH`；
    - 不在白龙马 probe 逻辑里新增战斗判断；
    - 战斗结束后走 `3f0a2e7` 的 post-battle / recover / next task 流程。

24. 总规则。  
    白龙马 probe 后半段的核心规则是：
    - 显形镜以后不睡、不 park、不放权；
    - Runner/provider 负责识别结果；
    - 队长只按四种业务结果走；
    - `wubei.probeNoTarget` 就是 no target，不再 tooltip fallback；
    - 第一个 probe 和第二个 probe 使用同一套结果分流；
    - 除了第 17 的 absent 规则和第 18 第四种 noTarget 规则，不顺手改其它业务逻辑；
    - 后续目标点击、入战、战斗等待、战后恢复都以 push `3f0a2e7` 为业务基线。

# 直接战斗模式（Alt+A）的授权、场景切换与二次截图

本章定义何时可以进入 `Alt+A` 直接战斗模式。`Alt+A` 的业务用途不是“已经找到点击点后附带按一次键”，而是
清空普通场景遮挡，使后续在直接战斗场景重新截图、重新定位可战斗目标。云端负责依据任务事实决定是否允许
切换；本地只执行获授权的输入、截图和返回坐标点击。

## 允许授权的两类任务事实

1. 五倍白龙马：当前 probe 已得到专用 `wubei.probeTargetReady`，即 Runner/provider 已确认白龙马出现。
   - 先关闭当前 Story 遮挡；这不是重新 OCR 或重新判断 probe，而是关闭已经确认的遮挡 UI。
   - 随后普通 `NPC_CLICK_SMART` FIFO 已完整消费，仍没有任何 verified target/combat action。
   - 此时允许进入直接战斗模式；不需要也不能要求云端先在被遮挡的普通场景截图中找到白龙马点击点。

2. 旧路线修罗或其它可战斗怪物：
   - 当前任务阶段明确目标 `targetRole=COMBAT_TARGET`；
   - 当前 canonical 地图与目标地图一致，且当前位置在该目标坐标的既有容差内；
   - 普通 `NPC_CLICK_SMART` FIFO 已完整消费，仍没有任何 verified target/combat action。
   - 这不是接任务 NPC 的近点直点规则，不能把两者混用。

## 禁止授权

以下情况绝不能进入 `Alt+A`：

- 接任务 NPC；
- 医宝宝、修装备、补给及其它维护 NPC；
- 非 `COMBAT_TARGET`；
- 新修罗 tracker 快捷路线。该路线仍只消费 tracker 的 `PREPARED_ACTION_READY`，不自己找怪、不进
  direct-combat；
- 仅有 `PATHING_TERMINAL`、仅地图相同、仅看见泛化 `STORY/OPTION`，但没有上述明确任务事实的情况。

## 执行顺序

1. 云端收到任务事实和普通 smart-click 的终态，返回独立 `ENTER_DIRECT_COMBAT` 或拒绝。
2. 本地仅在收到该授权后，经输入队列按 `Alt+A` 并使用既有短等待让场景稳定。
3. 本地重新截取绑定窗口 raw screenshot，并用 `directCombatMode=true` 启动新的云端
   `NPC_CLICK_SMART` session。
4. 云端在第二张、已进入直接战斗模式的截图中返回普通窗口相对目标 click；本地保持原子输入和原战斗 verifier。
5. 只有目标点击后 verifier 确认真实 `IN_COMBAT`，任务才进入 `WAIT_BATTLE_FINISH`。裸 `Alt+A`、裸目标点击、
   或仅 scene 切换都不构成入战成功。
6. 第二次 session 没有可执行目标或战斗 verifier 失败时，沿已有直接战斗失败后的重导航/重抽路径处理；不新增
   本地 full fallback，不改候选顺序、坐标容差或任务恢复语义。

## 与旧基线的关系

白龙马 `3f0a2e7` 原实现还通过 `GREEN_TEMPLATE_NOT_FOUND` 限制 direct-combat fallback。现在以“当前已确认
`probeTargetReady` 且普通 `NPC_CLICK_SMART` FIFO 全部未 verified”作为等价的业务门，用户已批准这一项替代。
除此以外，白龙马的 probe 四分支、Story 语义、坐标策略、候选顺序和失败恢复维持既有合同。

# 普通怪的逻辑

本文记录五倍普通怪任务的业务逻辑。普通怪不包含 `暗雷怪`、白龙马/显形镜 probe、黄袍怪/连战目标；这些都必须走各自独立逻辑，不能混进普通怪主线。

业务基线：普通怪现有业务判断仍以最近 push `origin/codex/migrate-runner-dialog` / `3f0a2e7` 为对照基线。后续迁移只能改 Runner/park/wakeup 的表达方式，不能顺手改普通怪的任务判断、目标名来源、点击顺序或入战条件。

## 到普通怪绿字寻路前

1. 队长接完五倍任务。  
   这里的前置条件是：接任务 NPC 和接任务对话框已经完成，本轮五倍已经进入“读左侧任务追踪”的阶段。

2. [Phase: READ_TRACKER]  
   队长读取左侧任务追踪，拿到这一轮最新 tracker panel。  
   这个读取结果是本轮普通怪判断的来源，不能复用上一轮或重抽前留下的旧 tracker panel。

3. 队长检查 tracker 黄字是否包含 `暗雷怪`。  
   如果包含 `暗雷怪`，这不是普通怪主线。  
   队长必须清掉当前 tracker panel，然后回到接任务路径重新接任务/重抽。  
   这里不能继续点绿字，也不能进入普通怪寻路。

4. 队长检查 tracker 是否是白龙马/显形镜 probe 任务。  
   如果是白龙马/显形镜任务，这不是普通怪主线。  
   队长必须进入白龙马逻辑，使用白龙马章节里的 probe 流程。  
   这里不能把白龙马当普通怪处理。

5. 队长检查 tracker 是否是黄袍怪/连战目标。  
   如果是黄袍怪或后续连战目标，这不放在普通怪主线里。  
   黄袍怪第一下可能也会点左侧绿字，但它的战后连战、补给窗口和续打规则独立于普通怪，必须单独整理。

6. 普通怪成立后，队长保存当前 tracker panel。  
   普通怪目标名来自左侧任务追踪黄字解析，不从当前游戏画面临时猜。  
   后续点怪、入战、fallback 都必须围绕这个 tracker 目标推进，不能把未知弹窗或移动状态直接解释成新的业务目标。

7. [Phase: TRACKER_PATHING]  
   队长点击左侧任务追踪里的第一条绿字，启动普通怪寻路。  
   这个点击动作只表示“开始按 tracker 去找普通怪”，不表示已经到达目标，也不表示可以进入战斗。  
   绿字点击必须保持为一次完整输入序列，不能把 move 和 click 拆成可被其他窗口插队的两段。

8. 普通怪 tracker 绿字的目标地图名必须由 `TaskTrackerPanelService` 从这条绿色链接文本本身解析出来。  
   这里不用 route hint，不用目的地浮窗，也不让队长额外读图。  
   解析结果先挂在当前 tracker 绿字段上，后续给 Runner 做后台地图名匹配和入战 interest 打开条件。  
   如果解析不到 `targetMapName`，不能伪造地图名，也不能把停下状态当作地图名匹配。
   暗雷怪在前置黄字判断里直接重抽，不参与这里的 `targetMapName` 解析；显形镜/白龙马不属于普通怪主线，
   即使它有两个绿字，也只能保留第一个绿字的地图名作为诊断，不能把两个 prompt 当成普通怪双目标。

## 普通怪绿字点击后的 Runner 等待

9. 队长点击普通怪绿字成功后，立刻放权。  
   队长交出当前 task turn，不再占用输入和调度权。  
   从这里开始，队长不自己读图、不自己判断弹窗、不自己判断移动。

10. 队长进入无限等待。  
   这里不是固定睡眠，不是 80ms 轮询，也不是 15 秒兜底。  
   队长一直等 Runner 返回明确结果。  
   没有 Runner 结果，就不回来继续业务。

11. Runner 接管观察当前窗口。  
    Runner 不直接点击，只负责观察当前窗口并返回结果。

12. Runner 每轮先看当前是不是 `OPTION dialog`。  
    只有 `OPTION dialog` 需要检查普通怪入战模板。  
    `STORY dialog` 和其他任何 dialog 都不管，直接忽略。

13. 如果当前是 `OPTION dialog`，Runner 尝试匹配普通怪入战模板。  
    如果匹配成功，Runner 准备 `WUBEI_ENTER_BATTLE` action，并发布 `PREPARED_ACTION_READY`。  
    队长收到后回来消费 action，点击进入战斗。

14. 如果当前是 `OPTION dialog`，但普通怪入战模板匹配失败：  
    Runner 不返回“模板未匹配”结果。  
    Runner 不叫醒队长。  
    Runner 直接跳过这个 `OPTION dialog`，继续判断当前是否停下。

15. 如果当前不是 `OPTION dialog`：  
    Runner 不处理这个 dialog。  
    Runner 不叫醒队长。  
    Runner 直接继续判断当前是否停下。

16. Runner 判断当前是否停下。  
    如果还在移动，Runner 只更新内部状态，不叫醒队长。  
    如果已经停下，Runner 返回 `PATHING_TERMINAL`。  
    队长收到后回去重新点当前普通怪绿字导航。

## 普通怪 Runner 结果处理

17. 普通怪等待阶段，Runner 只允许返回两类结果给队长：  
    第一类：`PREPARED_ACTION_READY / WUBEI_ENTER_BATTLE`。  
    第二类：`PATHING_TERMINAL`。  
    不再返回 `TASK_ATTENTION_REQUIRED`。  
    不返回“模板未匹配”。  
    不返回非 `OPTION dialog` 结果。

18. 如果 Runner 返回 `PREPARED_ACTION_READY / WUBEI_ENTER_BATTLE`：  
    表示 Runner 已经看到 `OPTION dialog`，并且成功匹配普通怪入战模板。  
    这个结果必须带着 prepared action：点击坐标、operation、target、matched/template 证据。

19. 队长收到 `PREPARED_ACTION_READY / WUBEI_ENTER_BATTLE` 后醒来。  
    队长重新拿到 task turn。  
    队长只消费这个 prepared action，不重新读图、不重新匹配模板。

20. 队长检查 prepared action 是否仍然属于当前窗口、当前任务、当前普通怪入战操作。  
    必须是 `operation=WUBEI_ENTER_BATTLE`。  
    如果不是当前窗口/当前任务/当前 operation，就不能点击。

21. 如果 prepared action 有效，队长点击 prepared action 给出的坐标。  
    这个点击就是普通怪进入战斗的唯一正常点击入口。  
    队长不自己另找怪，不自己跑 tooltip，不自己跑黄字 OCR，不自己跑 Alt+A。

22. prepared action 点击完成后，进入 `[WAIT_BATTLE_FINISH]`。  
    这里的含义是：入战点击已经执行，后面交给战斗状态观察。  
    队长不在这里重新点绿字。

23. `[WAIT_BATTLE_FINISH]` 阶段等待战斗状态。  
    如果 Runner/战斗守护确认已经进入战斗，就继续等战斗结束。  
    如果战斗还没结束，队长可以继续按战斗状态事件等待。  
    这里等待的是战斗状态，不是普通怪寻路状态。

24. 如果战斗结束，进入 `[POST_BATTLE_RECOVER]`。  
    普通怪战斗结束后不走黄袍连战续打。  
    普通怪只走普通战后恢复。

25. `[POST_BATTLE_RECOVER]` 完成后进入 `[RETURN_HOME]`。  
    队长按普通五倍战后流程回去。  
    回去以后继续下一轮接任务/读 tracker。

26. 如果 Runner 返回 `PATHING_TERMINAL`：  
    表示这一轮普通怪绿字寻路已经停下。  
    它不表示已经进入战斗。  
    它不表示有入战弹窗。  
    它也不区分“值得点怪”还是“停错地方”。

27. 队长收到 `PATHING_TERMINAL` 后醒来。  
    队长重新拿到 task turn。  
    队长不能进入 `ENTER_BATTLE`。  
    队长不能直接点怪。  
    队长不能跑 Alt+A。

28. `PATHING_TERMINAL` 的唯一正常处理是：  
    回到当前普通怪的绿字导航逻辑，重新点当前 tracker 的第一条绿字。  
    也就是说：  
    `PATHING_TERMINAL -> 重新点当前普通怪绿字 -> 再次放权等待 Runner`

29. 普通怪绿字重导航必须使用同一个 tracker panel / 同一个普通怪目标。  
    不能因为停了一次就重新读成别的目标。  
    不能把停下解释成任务完成。  
    不能把停下解释成要进入战斗。

## 入战前全局预算（CR266 用户批准替换旧"普通怪入战前超时"30-36 条，2026-07-11）

30. 预算从本轮"成功接任务"开始计时，固定 180 秒（3 分钟）。  
    计时起点不再是普通怪第一条绿字点击成功；它覆盖接任务之后的 maintenance、读 tracker、
    绿字点击、导航、`ENTER_BATTLE` 以及所有内部 wait/retry。  
    热启动轮（本轮没有经过接任务、直接续跑已接任务）保留旧的"第一条绿字点击成功"起点兜底。  
    暗雷 reroll 重接不重置预算：本轮第一次接任务成功的时刻是唯一起点。

31. 预算超时由 Runner 检查并发布。  
    队长不靠自己轮询检查超时。  
    用户暂停/恢复期间，暂停阻塞时长必须补回预算（与既有 pause timer compensation 语义一致）。

32. 如果预算内 Runner 成功准备 `WUBEI_ENTER_BATTLE`：  
    Runner 发布 `PREPARED_ACTION_READY`。  
    队长回来消费 prepared action，点击进入战斗。  
    注意：点击进入战斗**不结束预算**；预算只在 Runner 首次确认 `IN_COMBAT` 时结束（见 36）。

33. 如果预算内 Runner 只返回 `PATHING_TERMINAL`：  
    `STOPPED_AWAY` 必须先过"该绿字点击 intent 已有真实移动确认"这道事实门（CR266 第 2 项）；
    没有移动事实时回同一条绿字重新导航，不得进入 `ENTER_BATTLE`。  
    计时不重置，仍从本轮接任务成功开始算。

34. 如果 180 秒到了，Runner 仍未首次确认 `IN_COMBAT`：  
    Runner 发布 `PRE_BATTLE_TIMEOUT`。  
    这是入战前预算超时的明确事实事件。  
    它不是 `TASK_ATTENTION_REQUIRED`，也不是 `PATHING_TERMINAL`。

35. 预算优先级高于一切内部循环。  
    队长无论正处于哪个 phase 或内部 `waitForPrepared...` 等待（含 probe story / probe
    enter-battle / prepared-dialog reply），都必须立即消费该超时：清 task-owned
    dialog/prepared/pathing/interest/runtime，直接回到重新接任务入口
    （`ROUTE_TO_MAIN_TASK`）。不能只在普通 phase boundary 检查，不能因只监听
    `PREPARED_ACTION_READY` 而漏掉 timeout。

36. Runner 首次确认 `IN_COMBAT`（或确认战斗已发生并结束，`EXIT_RECOVERED`）时预算结束。  
    战斗时长不受本预算限制；战斗持续超过三分钟不得触发回接任务。  
    战斗中只走战斗状态等待自己的逻辑。

# 黄袍怪的逻辑

本文记录五倍黄袍怪/连战任务的业务逻辑。黄袍怪第一战入战前可以沿用普通怪的 Runner/park/wakeup 框架；真正不同从第一次进入战斗以后开始：黄袍怪战后可能原地连战，不能像普通怪一样战斗结束就回城。

业务基线：黄袍怪现有业务判断以最近 push `origin/codex/migrate-runner-dialog` / `3f0a2e79007121c98a15ad90d5ed7b8902033068`（短 ID `3f0a2e7`）为争议裁决基线。后续如果对黄袍怪连战、补给窗口、绿字点击、入战等待或回城条件有争议，先对照这个 push；除非用户明确批准新的行为变更，否则不能把本地迁移改动当成业务基线。

## 黄袍怪第一战入战前

1. 队长接完五倍任务。  
   前置条件同普通怪：接任务 NPC 和接任务对话框已经完成，本轮五倍进入 `[READ_TRACKER]`。

2. [Phase: READ_TRACKER]  
   队长读取左侧任务追踪，拿到这一轮最新 tracker panel。  
   这个 tracker panel 是本轮黄袍怪判断来源，不能复用上一轮或战后旧 panel。

3. 队长检查 tracker 黄字。  
   如果黄字包含 `暗雷怪`，这不是黄袍怪主线，按暗雷重抽逻辑处理。  
   如果 tracker 是白龙马/显形镜 probe，这不是黄袍怪主线，必须进入白龙马逻辑。  
   如果黄字包含 `黄袍`，这轮进入黄袍怪逻辑。

4. 黄袍怪成立后，队长保存当前 tracker panel，并标记本轮是连战任务。  
   黄袍怪目标判断来自左侧任务追踪黄字里的 `黄袍`，不是从当前场景临时猜。  
   后续战后是否继续，也只信战后重新读取到的 tracker panel。

5. [Phase: TRACKER_PATHING]  
   第一战入战前，队长点击左侧任务追踪里的第一条绿字。  
   这个点击动作只表示“开始按 tracker 去找第一只黄袍怪”，不表示已经到达目标，也不表示可以进入战斗。  
   绿字点击必须保持为一次完整输入序列，不能把 move 和 click 拆成可被其他窗口插队的两段。  
   黄袍第一战 tracker 绿字的 `targetMapName` 来源同普通怪：由 `TaskTrackerPanelService`
   从绿色链接文本本身解析，不用 route hint，不让队长额外读图；后续只给 Runner 做后台地图名匹配和
   入战 interest 打开条件。

6. 第一战入战前，黄袍怪可以沿用普通怪的放权等待模型。  
   队长点击第一条黄袍绿字成功后，可以交出当前 task turn，并等待 Runner 返回明确结果。  
   这是因为第一战前仍然属于“找第一只怪”的长寻路阶段。

7. 第一战入战前，Runner 的结果边界同普通怪。  
   Runner 只把 `OPTION dialog` 中成功匹配 `WUBEI_ENTER_BATTLE` 的情况返回为
   `PREPARED_ACTION_READY / WUBEI_ENTER_BATTLE`。  
   `OPTION` 模板未匹配、`STORY`、其他 dialog 都不是黄袍怪业务结果，不叫醒队长；Runner 继续判断是否停下。  
   如果 Runner 返回 `PATHING_TERMINAL`，队长只重新点同一个黄袍 tracker 绿字。

8. 第一战入战前沿用入战前全局预算（CR266 起：接任务成功起算 180 秒，热启动轮以第一条绿字
   点击兜底起算），到 Runner 首次确认 `IN_COMBAT` 结束。  
   如果预算内没有进入战斗，按入战前预算超时处理，回到重新接任务路径。  
   这个计时只覆盖第一战入战前，不覆盖黄袍怪连战中的战斗时间。

9. 如果 Runner 返回 `PREPARED_ACTION_READY / WUBEI_ENTER_BATTLE`，队长回来消费 prepared action。  
   队长只点击 Runner/provider 给出的 prepared 坐标，不自己另找怪，不自己跑 tooltip，不自己跑黄字 OCR，不自己跑 Alt+A。  
   识别到这个入战 dialog 并准备消费时，必须立刻关闭当前五倍维护窗口；维护窗口不能拖到第一战结束以后再关。  
   prepared action 点击成功后进入 `[WAIT_BATTLE_FINISH]`。

10. 一旦第一次成功点击 `WUBEI_ENTER_BATTLE` 并进入 `[WAIT_BATTLE_FINISH]`，黄袍怪进入连战热路径。  
    从这个点开始，普通怪的“点击绿字后无限 park 等 Runner 结果”模型不再适用于本轮黄袍怪连战。

## 黄袍怪第一战后的连战热路径

11. [Phase: WAIT_BATTLE_FINISH]  
    队长等待第一场黄袍怪战斗结束。  
    战斗中可以按现有战斗状态等待机制释放/等待；这里不是黄袍怪续战绿字的无限 Runner 等待。

12. 战斗结束并恢复后，进入 `[POST_BATTLE_RECOVER]`。  
    如果本轮是黄袍怪，不能按普通怪直接回城。  
    黄袍怪战后进入连战热路径：队长确认本场终态脱战后，开启 5 秒队员补血/补蓝窗口的同时，向已绑定
    本地同队成员广播本场 `FREE`；成员据此进入既有战后预检/补给链。候选快脱战不得广播。队长同时在
    后台准备下一步判断。

# [BR-WUHAN-005] 五环一次性 FrameDemand 与 Prepared Action 精确消费

## 2026-08-02 已批准的 Runner / Cloud 交接合同

五环的业务判断仍归 Cloud；Runner 不是 phase 驱动器，也不是本地大脑。它只观察绑定 HWND、执行 Cloud command、回执执行结果。任何唤醒都必须已经有 Cloud 创建的唯一 `PreparedAction`，不能再用裸 `TASK_ATTENTION_REQUIRED` 叫醒主循环。

1. Runner 只观察 `pathing started / ARRIVED / STOPPED_AWAY`、`IN_COMBAT / COMBAT_EXITED`、五环 title 的 present/absent、dialog presence。它不决定绿链、dialog、回城、重试或 phase。

2. 本地确定性命中五环 title `present` 时，在**同一个 observation request**附带恰一张当前 Tracker 图；该图严格绑定 `taskRunId/windowId/hwnd/observerSeq`。它不是 `tracker changed`，也不是每秒上传的订阅图。

3. title `absent` 只上报事实。Cloud 先检查是否有需要完成的 dialog 链；Cloud 可以决定请求一次 dialog 图来区分 `FINISHED`、`FINISHED_ONCE`、`DAILY_LIMIT`，或按既有无 Tracker 业务分支处理。Client 不自行完成/回城。

4. dialog presence 也只上报事实。Cloud 以唯一 `demandId` 索要一张 exact-HWND dialog 图，使用该图生成唯一 `actionId` 的 `PreparedAction`；Client 只执行该 command 并回执。demand 被消费或 action 回执后，旧 demand、旧图、旧 action 必须在两侧拒绝。

5. `ARRIVED` / `STOPPED_AWAY` 的终态帧可按现有终态通道一次性携带给 Cloud 作 NPC action 决定；五环不得存在 `wuhuan-tracker` 常驻每秒上传，也不得借用 `xiuluo-dialog` 两秒上传。

6. dialog presence 已出现时，Cloud 必须先走完 `presence -> FrameDemand -> frame -> action -> ack`，期间不得生成竞争的 Tracker action。dialog action 后等下一条 title 事实，再处理绿色链接。

7. `PREPARED_ACTION_READY` 只是已经存在 action 的通知；五环主循环只消费自己当前窗口、当前 run、当前 `actionId` 的 action。`TASK_ATTENTION_REQUIRED`、普通图像变化或其他窗口的 ready 事件均不得单独唤醒/推进五环。

8. 完成 story 语义保持不变：`wuhuan_task_finished_story.png` 表示今日彻底结束；`wuhuan_task_finished_once_story.png` 表示本次完成、是否下一轮仍由既有次数配置决定。接任务 option、买鞋/交鞋 option 与完成 story 仍由 Cloud 识别和判定。

9. prepared frame 的“传输成功”与 prepared action 的“发布/消费完成”是两个不同的 ACK 边界。同一
   `demandId + generation` 的图片一旦随 observation HTTP 请求成功送达 Cloud，Client 必须记为已交付；只要
   demand 代次未改变，就不得在后续 observation 中重复附带相同 PNG。只有传输请求失败时才保留同帧并按观察
   通道既有失败退避重试；新 demand、replacement generation 或显式 cancel 才重置交付状态。

    观察或物理输入，也不得改变返回给业务的原始截图/匹配结果。

# [BR-START-001] 战斗中启动与暂停恢复任务的逻辑

**2026-09-10 用户追加批准：普通失败原任务恢复，致命失败允许自动重启同任务。** 普通没匹配上、没点成功及内部phase失败仍走该任务已有的同run/同轮有界恢复，不得以热启动代替。明确的`TaskFatalException`终止属于例外：Cloud须在推进下个队列任务前收束该失败；Client先确认旧Cloud运行终止、旧观察及维护执行退出，撤销旧任务输入并清执行/现实缓存，再重启失败任务和其后尚未执行的队列，保留该任务已完成次数/总次数，失败不得记成功，不重复前面已完成的队列任务。清理尚未确认时保留恢复待办并退避重试，不带旧执行强行启动。不能仅凭FAILED/SKIPPED或错误文本推定致命；非致命终态不通过此例外重建任务。用户暂停/停止/新启动必须作废旧恢复待办；切号、窗口几何安全边界继续有效。UI真正启动/暂停恢复和正常SUCCESS配置次数续跑不变，不增设仅管Alt+Q的字段。本段替代此前“所有失败终态一律等UI”的暂定规则；数值进度仅在同窗、同任务、同总数恢复，其他终态仍按既有清理规则。

本文记录用户在游戏窗口已经处于战斗画面时，首次启动或从 `PAUSED` 恢复修罗、五倍、天庭、鬼王及同类主任务的通用业务规则。它和任务运行中途的 `INCIDENTAL` 战斗不是同一个场景：新的 task run 尚未完成当前画面仲裁，也不能信任战斗画面里的队伍/位置/UI/Tracker 状态。

1. 用户在战斗中点击首次启动或暂停恢复时，通用启动层必须先等待 Runner 对当前 exact run/window/HWND 给出明确战斗状态。新建 `GameContext.State` 的默认 `FREE` 不是证据，不得据此放行任务。
   如果已经在战斗中，不做队伍角色检测，不信任旧的 leader/member/solo 状态，不做 `syncMyPosition()`，也不做启动前 UI 准备，例如 Alt+1、Alt+6、地图设置、任务栏调整等。

2. 任务进入通用“启动等待战斗结束”状态。
   这个状态不算任务停止，不算任务失败，也不应该触发 leader-only 策略把任务 skip 掉。等待期间屏蔽任务自己的 Dialog/Tracker/回程/导航 probe，只维护自动战斗并等待 Runner 的 `COMBAT_EXITED`；正常响应用户停止/暂停。

3. Runner 确认脱战后，通用门还必须等到一份晚于脱战边沿的新 observation frame，才允许任务读取 Dialog/Tracker。战斗帧中的 `title=absent`、`dialog=none` 或其他 negative 一律过期。首次冷启动随后重新跑正常启动前置；暂停恢复沿用已保留 identity，禁止补跑冷启动 UI 前置。

4. 前置完成后，任务进入“战斗后启动恢复”流程。  
   第一件事是读取左侧任务追踪。如果左侧 tracker 里仍然有当前任务的目标/绿字，例如修罗任务或五倍目标，说明刚才那场战斗没有完成当前任务，或者不是当前任务期望的战斗。此时按当前任务的正常维护规则检查补给/修理/状态，检查完成后继续点击左侧 tracker 绿字推进任务。

5. 如果左侧 tracker 里没有当前任务目标/绿字，下一步才尝试使用当前任务对应的回程道具。  
   修罗使用修罗自己的回程道具；五倍使用五倍自己的回程道具。能找到就使用，找不到就说明身上大概率没有这个任务，直接回到起点/接任务流程。

6. 如果找到并使用了任务回程道具，且成功回到预期地图，则认为刚才那场战斗大概率已经完成了当前任务。  
   后续进入当前任务的正常战后流程，例如回起点、归队/归位检查、下一轮接任务。这里不是简单地把战斗忽略掉。

7. 如果找到了任务回程道具，但使用后没有回到预期地图，说明身上可能仍有任务，但 tracker/地图状态已经不可靠。  
   为了避免复杂热启动误判，修罗和五倍都走简单恢复：直接回城/回起点，然后重新进入接任务流程，不继续沿用刚才的任务状态。

8. 这个启动恢复流程不能改变任务内部已经验证的战斗来源规则。  
   例如修罗快捷路线里，通过 `TRACKER_CONFIRM` 进入的战斗仍然按快捷路线的已确认战斗处理；任务运行中途的 `INCIDENTAL` 战斗仍按该章节自己的规则恢复。本节只约束“用户在已经战斗中点击启动任务”的外层启动流程。

9. 天庭有限次数任务在暂停时必须把“可执行瞬时状态”和“累计完成次数”分开处理。
   暂停仍清除旧 run 的路径、点击、对话、观察、战斗和 phase 等瞬时状态，但 exact window 当前天庭任务的数值型
   `completed/total` 必须留作 `PAUSED` UI 与下一次热恢复使用。只有同一窗口、同一任务、同一有限总数的
   `PAUSE_RESUME` 可以把累计次数交给 Cloud；Cloud 天庭业务计数、`GameContext` 和首次 UI 进度必须从同一个值
   初始化，循环按剩余次数结束。STOP、冷启动、任务终态、任务或总数变化，以及成员实际任务投影成
   `AUTO_BATTLE` 时均从 `0` 开始，禁止跨窗口或跨任务复用。后续李靖“今日已完成次数”OCR 只允许按既有规则向上
   校准，不能把已恢复的累计次数向下覆盖。

# [BR-DIALOG-001] 未知 Phase 的 Title/Dialog 仲裁与绿链无移动恢复

本规则只用于恢复一个已经失去可信业务 phase 的任务现场，不是常驻检查。允许进入的入口只有两类：启动、
暂停恢复或热接时没有可信 phase；以及已知 phase 的关键动作没有产生它唯一应产生的结果，例如本次 exact
Tracker 绿链点击在既有有界证明窗口内明确没有启动移动。正常 phase、正常移动、正常进战、正常脱战和普通
`STOPPED_AWAY` 本身都不能启动本规则。

1. 仲裁必须从同一个 observation lineage、同一个 exact HWND、同一个 `observerSeq/evidenceId` 同时取得当前
   任务 Title 和 Dialog 两份事实。Title 使用 `PRESENT | ABSENT | UNKNOWN`；Dialog 使用
   `NONE | OPTION | STORY | UNKNOWN`。`PRESENT`、`ABSENT`、`NONE`、`OPTION`、`STORY` 都是确定终态；
   只有 `UNKNOWN` 可以在当前有界预算内重查。任何 `UNKNOWN` 都禁止猜 phase 或点击。

2. 启动/暂停恢复/热接时，Dialog 为 `OPTION` 必须优先交给 Cloud 当前任务的候选目录处理。命中的候选返回
   稳定 `actionKey`，任务依据 `(taskCode, actionKey)` 进入对应验证 phase；本地模板若已经执行已知点击，只
   上报 exact run/window/HWND/evidence 下的 `actionKey`，不能自行修改 Cloud phase。候选全部 miss 时只走
   现有 Cloud Dialog fallback；本地没有关闭未知 Dialog 或上报 `DIALOG_DISMISSED` 的能力。fallback 完成后
   继续使用本轮已经取得的 Title 事实，不重读 Title。Story 仍按各任务已有显式目录和终态规则处理。

3. 本次 exact Tracker 绿链点击明确没有启动移动后，重新取得同 lineage 的 Title/Dialog：Title 存在且无
   Dialog 时保持 Tracker phase，走该任务既有有界无移动恢复；Title 不存在时旧 Tracker action 立即失效，
   禁止复点，按任务自己的无任务、完成或重新接取规则重定 phase，若同时有 Dialog 才使用启动候选目录。
   Title 存在且有 Option Dialog 时默认使用现有 Cloud fallback 清障，不得取消当前任务；但天庭保留 G014
   已验证的任务例外：只有本次 exact 绿链未启动移动时，先启用本地七张已知模板恢复探针，命中后上报稳定
   `actionKey` 并由 Cloud 复用既有天庭业务 consumer；七张全部 miss 才允许一次 Cloud fallback。该例外不得
   扩展为常驻扫描，也不得用于其他任务。

4. 本次 click-no-movement 必须复用当前任务已有的 exact movement proof、同一 action/attempt 身份、有界预算
   和防重复点击机制。此前一次移动留下的 `STOPPED_AWAY` 不能作为本次新点击未移动的证据；旧 run、错 HWND、
   旧 evidence、未知 `actionKey`、仅匹配未执行或已被另一侧消费的动作一律拒绝。

5. Client 本地已执行动作与 Cloud `PreparedDialogAction` 对同一 evidence 必须一胜一负。本地动作先完成时撤销
   对应 Cloud 等待和过期 action；Cloud action 已消费时本地 one-shot 不得再点击。本地 enter-battle 点击只进入
   `WAIT_COMBAT`，仍须 Runner 的真实 `IN_COMBAT`；本地 accept 点击只进入接取后的 Title/Tracker 验证，不能

# [BR-START-002] 有专属回程道具任务的通用 Hot Start Policy

本 Policy 适用于修罗、江湖历练、鬼王、天庭、五倍以及后续任何实际拥有专属任务回程道具的任务，在完整启动、暂停恢复后的任务内恢复中统一执行。它只判断当前任务从哪里继续，不包含窗口启动前置检查；不能在这里规定 `Alt+1`、`Alt+5`、`Alt+6`、地图/飞行开关检查或其他启动准备动作。没有专属回程道具实现的任务（当前抓鬼）不凭空新增包裹扫描。

暂停恢复和首次冷启动必须分开。pause 会终止旧 run 并清除旧 phase、事实、待执行输入和观察 lineage，但保留
exact HWND 绑定、已确认角色、已选任务和玩家身份。用户从 `PAUSED` 点击继续时，应直接以这些 lifecycle identity
创建全新 run，并按当前画面执行本 Policy；不得重新发现窗口，不得执行 `Alt+T` 队伍预检、包裹页校准或公共启动
UI 前置。若当前仍在战斗，只进入任务自己的战斗等待 phase；真正脱战后直接继续本 Policy 的 dialog/tracker/回程
道具恢复顺序，不再补跑冷启动前置。保留 identity 缺失时明确失败，不允许临时打开可见 UI 猜角色。

1. 先判断当前窗口是否已经在战斗中。
   如果已经在战斗中，进入当前任务自己的战斗等待 phase；不读取 dialog、tracker，不使用回程道具，不尝试任务目标导航。

2. 非战斗时，处理当前 dialog。
   每个任务声明自己关心的 dialog interest 与对应结果。dialog 处理必须返回明确的“业务动作 + 下一 phase”：已知 dialog 直接执行该任务定义的动作并进入对应 phase；`STORY_DIALOG` 是否保留、忽略或消费，由任务自己的 dialog 规则定义；未被当前任务关心的 `OPTION_DIALOG` 关闭后，才继续下一条热启动事实。未知 dialog 不得被当作已接任务、已入战或可继续导航的证据。

3. 如果没有需要处理的 dialog，检查是否存在队伍回归信号。
   如果存在，进入当前任务的 `WAIT_TEAM_RETURN`；在回归信号消失前，不读取 tracker、不使用回程道具、不继续任务上下文导航或重新接任务。

4. 如果没有队伍回归信号，读取当前任务自己的左侧 tracker。
   如果存在可用绿链，点击绿链并进入该任务已经定义的 tracker 路线；不优先使用旧任务上下文。

5. 如果没有当前任务 tracker，尝试使用当前任务自己的回程道具。
   回程道具使用并验证成功后，进入该任务定义的战后回程、归队或下一轮流程。
   这一步对首次 NORMAL Hot Start 同样强制；不得仅在 `AFTER_COMBAT_EXIT_STARTUP` 执行。只有明确的
   `CLEAN_QUEUE_TRANSITION` 可以继续沿用“上一队列项已闭合，当前任务直接新接取”的既有边界。

6. 回程不可用或未验证成功后，消费当前任务可恢复的已保存上下文。
   任务可定义自己的恢复事实，例如已保存 objective、后台解析结果或其他已验证任务状态；存在时进入该任务对应的恢复 phase。

7. 所有事实都不能恢复当前任务时，清理必要 UI，进入该任务自己的接任务入口。

8. 固定总顺序为：
   `战斗中 > 当前任务 dialog 分类 > 队伍回归信号 > 当前任务 tracker 绿链 > 当前任务回程道具 > 当前任务已保存上下文 > 当前任务接任务入口`。

4. 如果接任务后维护没有到时间，队长不等待 tracker 解析完成，先启动灵兽村出村预路径。

5. 如果接任务后维护已经到时间，先按现有维护逻辑处理。

## 非快捷路线

本节只记录修罗 V2 的非快捷路线。非快捷路线也是快捷寻路路线不能启动或失败后的完整 fallback；不能用非快捷路线规则反推快捷路线中途行为。

1. 队长接修罗任务并成功点击接任务 option 后，立即截取一次 story objective 快照。  
   这一步只负责拿到接任务后当前画面的目标文本区域快照，不重新跑完整 dialog detect，不重新点击，也不在这里同步解析目标。

2. 截图成功后，把这张内存图交给后台解析目标地图和坐标。  
   后台只解析这张已经截好的图；不能再截图，不能发输入，不能关闭或打开 UI，也不能再走一套 `handleDialog(READ_STORY_OBJECTIVE)`。

3. [Phase: READ_OBJECTIVE]  
   `READ_OBJECTIVE` phase 保留，但它的职责改成“等待并消费接任务后那张快照的后台解析结果”。  
   这是替换旧的目标读取实现，不是在旧实现旁边再加一套后台逻辑。  
   改完以后，`READ_OBJECTIVE` 里面不能再截图，不能再跑 dialog detect，不能再调用 story objective 读取，也不能再读 task panel。  
   进入这个 phase 后，队长必须等后台解析完成，不能放权、不能 park、不能 yield，也不能让其他窗口或队员插队。  
   这个 phase 只有两种结果：目标解析成功，或者目标解析失败。

4. 在后台解析目标的同时，队长可以继续非快捷路线的出村预路径。  
   也就是接任务后先启动离开灵兽村的动作，例如打开小地图、点击灵兽村出口。  
   这一步不等目标解析完成，但它不能替代第 3 点：一旦进入 `READ_OBJECTIVE`，必须等待后台解析的成功或失败结果。

5. 如果后台解析成功，队长把目标地图和坐标写入当前修罗 round context，然后进入 `NAVIGATE_TO_TARGET`。  
   如果出村预路径已经启动，就沿用这个状态继续后续目标导航，不再重复做一套目标读取。

6. 如果后台解析失败，本轮非快捷路线按“目标读取失败”处理，进入修罗失败恢复或重新接任务路径。  
   不允许在同一个 `READ_OBJECTIVE` phase 里再补一次截图、dialog detect、story objective OCR 或 task-panel OCR；失败就是失败，按恢复路径走。

7. 非快捷路线不允许“两边同时算”。  
   一旦接任务后的后台快照解析已经启动，前台 `READ_OBJECTIVE` 只能等待并消费这个后台结果。  
   `READ_OBJECTIVE` 不能并行调用 `DialogService.handleDialog(READ_STORY_OBJECTIVE)`，也不能再让 task 自己重新读取目标文本。

8. 如果接任务后的快照没有拿到，例如截图返回空、窗口绑定异常、截图服务失败，则视为后台解析失败。  
   这里不在同一轮里并行补拍第二张图；是否以后增加新的恢复卡，单独讨论。

9. 本节只改变修罗非快捷路线里“目标读取”和“出村预路径”的重叠方式。  
   不改变修罗目标导航、NPC 点击、入战确认、维护广播、回城、战斗等待、任务完成判断等后续业务顺序。

## 失败 fallback 逐阶段规则（基线对账，2026-07-08）

本节是修罗云端单脑迁移的失败处理基线事实：迁移前全本地业务基线（git `696a12b0ffb8aa21f7d5dee841a65cecd78be9f7` 的 `XiuluoTaskV2.java`，下称基线，`L` 为其行号；其子提交 `dc4394f` 只是云端迁移计划文档提交，不作为业务基线，两者 `src/` 完全一致）每个 phase 失败时怎么处理。表中"云端缺口"列是 2026-07-08 对账快照（对照外部 `dhxy-cloud-brain` `DecisionEngine.nextXiuluoBrainCommand`）；缺口修复进度以 `docs/PACKAGE_ARCHITECTURE.md` Card CR230 为准，某项修完后应回来把该格更新为"已对齐"。

### 通用恢复骨架（所有 phase 共用）

1. 失败先原地重试 1 次（`MAX_PHASE_RETRY=1`，L167）。
2. 再 `cleanUpAll` 后跳到该 phase 的恢复 phase，恢复跳数上限 `MAX_RECOVERY_COUNT=2`（L168；`retryCurrentOrRecover` L3321，`recoverOrFail` L3344）。
3. 预算耗尽产出 FAILED，由主循环 `restartRoundAfterPhaseFailure`（L683）兜底：归档失败 case + `consecutiveRoundFailures++` + `cleanUpAll` + 交出任务回合 + 重开同一轮（round 号不递增）。
4. 同一轮连续失败满 10 次（`MAX_CONSECUTIVE_ROUND_FAILURES=10`，L169）抛 `TaskFatalException`，整个任务终止（L719/L725）。普通失败永远只重开轮，不终止任务。
5. loop guard：一轮内非寻路/非共享态的连续推进超过 32 步（L569）→ `restartRoundAfterLoopGuard`（L704）重开同轮；寻路/共享态会清零计数。
6. 进战前 watchdog 180 秒（L177）：适用白名单 phase（L642-666），明确排除 `WAIT_COMBAT`、`RETURN_HOME`、`NAVIGATE_BACK_TO_START`、`WAIT_TEAM_RETURN` 和终态；超时按 phase-FAILED 重开轮；维护/暂停时长会补偿回起算点（L982）。
7. 未捕获异常 → `restartRoundAfterUnexpectedPhaseException`（L670）→ 重开同轮。
8. STOP / 暂停中断 / 用户手动停止永远不是业务 FAILED。基线里 INTERRUPTED 一律走 stopped（如 `ACCEPT_TASK_DIALOG` L1202、维护检查 L1298/L1390），任务以 STOPPED 结束、UI 无异常。云端等价实施时，stop/pause fact 不得被 cloud-required failure 包装成异常结束（关联 CR228 的 stop 语义修复）。

# [BR-NPC-001] NPC Click 云端 FIFO 候选队列逻辑

## 2026-09-10 G173 最新裁定：全任务禁用紫名点击

用户明确要求所有通过紫色玩家名产生点击的方法全部禁用。本节覆盖下方及历史文档中仍记载的紫名公式、紫色blob点击、紫名衍生Ctrl探测及以紫名定位退出Alt+A的旧步骤，不按任务白名单启用。所有入口不再为产生这些点执行紫名OCR；旧队列/预备plan残留紫名候选也必须跳过且不得输入，继续其它合法候选。`PURPLE_FORMULA`枚举和历史记录可保留用于兼容解码，不代表可执行。

普通FIFO顺序改为`MEMORY -> TOOLTIP -> YELLOW_NAME -> CTRL_CANDIDATES -> END`；固定点等已批准profile顺序保持，仅剔除紫名策略。黄字需名字层replacement的既有闭环保留，但不会先做紫名公式。直接战斗退出保留既有窗口中心右击及退出验证，不再寻找紫名。永久成功记忆不删除、不按旧来源作废；黄字ROI学习的紫名联合证据只作区域证据，不产生点击，因此本次不改其语义。

本文记录 `NPC_CLICK_SMART` 云端化后的最终业务模型。它覆盖普通 NPC 点击、修罗/五倍接任务 NPC、目标 NPC、以及后续复用 `NpcClickService` 的同类入口。当前结论以 2026-07-03 用户定稿为准，早前“云端逐步要求本地执行 action/outcome”或“云端重写一整套视觉识别并直接返回最终点位”的半截方案都作废。

## 基本职责

1. 本地仍负责真实窗口操作。
   本地负责窗口绑定、`Alt+4`、截图、输入队列、鼠标点击、Ctrl hover/menu 本地动作、pause/stop、坐标越界校验和点击后 verifier。

2. 云端负责 NPC click 的策略脑子。
   云端负责 learned memory、tooltip、黄字、紫名公式、Ctrl 候选等候选顺序、候选计算、候选去重、失败后的下一候选选择，以及成功/失败后的记忆和指标。

3. 本地旧 pipeline 必须保留为 shadow/reference。
   它不能作为生产 full fallback 接管执行；生产点击只能来自云端 session queue 消费到的候选。旧 pipeline 的意义是回放、对比、review 和后续排错，不允许因为“no local fallback”就物理删除。

4. NPC Click 不拥有后续 dialog 业务。
   点击后的 expected dialog / combat verifier 是本地验证点击是否成功的 outcome 来源；真正 dialog option 怎么点、任务 phase 怎么走，仍归对应任务和 `DialogService` 处理。不能把 post-click dialog 业务混进 NPC click 云端脑子里。

## 成功坐标永久栈与单次启动工作栈

1. Cloud 对每个 exact 场景维护一份永久成功坐标栈。场景键至少包含地图、NPC、目标地图坐标、验证模式和玩家地图坐标；这份数据只允许追加经过本地 verifier 明确验证成功的窗口相对点击坐标。

3. 点击失败、验证失败、超时、取消或未知结果都不得删除、降权、标记过期或重排永久成功坐标。Client 只执行候选并报告 outcome，不拥有也不直接修改永久数据；持久化写入由 Cloud 独占，且失败 outcome 不得改写成功坐标集合。

4. **2026-09-13 G180用户定案覆盖旧弹栈规则，见下方BR-NPC-003。** Cloud记忆服务在程序启动时从永久成功坐标建立临时副本；读取、下发和成功使用不删除点，成功点不限轮次/次数持续复用。不得按taskRunId/round/session重建或补回此副本。

5. 同一场景仍按LIFO产生候选，单次FIFO内用独立的“已尝试”记录推进，不能修改启动副本的可用点集合；本次候选尝试完才继续tooltip/黄字/有效Ctrl后备策略（紫名已由G173禁用）。成功只结束当前session，下次仍可使用该点。

6. 兼容旧数据时，只能从历史强验证成功样本或已有的已验证成功点初始化永久成功坐标栈；旧的 `failureStreak`、`stale`、最近一次失败和失败计数不得再决定坐标能否进入启动副本。

### 既有session执行顺序（其它规则不变）

1. 本地准备点击普通 NPC 时，先做必要安全检查：request 非空、`npcName` 非空、窗口/hwnd/base 有效、任务上下文有效。

2. 普通初始场景下，本地按一次 `Alt+4` 清理名字显示，然后截取一张绑定游戏窗口的 base screenshot。
   这张图是本次 NPC click session 的基础图。主链路不允许每个策略都重新截图，也不允许云端要求本地反复补图来绕过策略不等价问题。

3. 本地向云端发起一次 `NPC_CLICK_START` session 请求。
   request 至少携带：`sessionId`、`npcName`、任务/source、当前玩家坐标、目标地图/坐标、scan regions、base screenshot、窗口尺寸/坐标空间、验证模式和必要上下文。

4. 云端收到 `NPC_CLICK_START` 后创建 FIFO candidate queue。
   云端按旧稳定 pipeline 顺序生产候选，并且每算出一段就 push 到 queue，不等所有策略算完才统一返回。
   没有点击点的 miss 可以立即进入下一策略；一旦 push 出真实可点击候选，该候选就是生产栅栏，Cloud 不得在
   Client 处理它之前启动后续策略的 OCR/template/Ctrl 计算。

5. queue 的业务顺序固定为：
   `MEMORY` -> `TOOLTIP` -> `YELLOW_NAME` -> `PURPLE_FORMULA` -> `CTRL_CANDIDATES` -> `END`。
   实现可以按代码风格命名消息类型，但业务顺序不能变。

6. 本地是 FIFO consumer。
   本地只按 queue 顺序消费消息，不自己决定“tooltip 失败就试黄字、黄字失败就试紫字”。下一步用哪个候选，必须来自云端 queue。

7. `MEMORY` / `TOOLTIP` / `YELLOW_NAME` / `PURPLE_FORMULA` 这类普通点击候选必须返回窗口相对点击点、候选框、策略名和证据摘要。
   本地校验坐标属于当前窗口和允许区域后，用输入队列执行原子 move+click，然后运行本地 verifier。

8. `CTRL_CANDIDATES` 表示云端给出一组 Ctrl probe 起点或候选操作。
   本地负责按旧本地 Ctrl/menu 动作执行 hover、菜单匹配和点击。Ctrl hover 后不需要再把截图发回云端；这部分真实输入和菜单匹配仍在本地执行，但是否进入 Ctrl 阶段、候选点有哪些，由云端 queue 决定。

9. `END` 表示本轮云端已经没有候选。
   本地消费到 `END` 且此前 verifier 都失败时，本次 NPC click 失败，不能再跑旧本地 pipeline full fallback。

## 成功、失败和回报

1. 本地每执行一个候选后，只用 verifier 判断点击是否成功。
   verifier 成功可以来自 expected dialog、expected combat、或当前调用方已有的验证规则；它只产生成功/失败 outcome，不改变 NPC click 策略顺序。

2. 一旦 verifier 成功，本地立刻停止消费 queue，进入下一步任务/dialog 流程。
   同时异步向云端报告成功 outcome，用于 learned memory、候选降权/升权、指标和日志。这个成功回报不需要阻塞任务继续运行。
   Cloud 必须终止该 producer 并丢弃尚未消费的同 session 消息；成功候选之后的黄字、紫字或 Ctrl 识别不得启动。

3. 如果 verifier 失败，本地继续消费下一个 FIFO 消息。
   本地可以把失败 outcome 异步/同步回报云端，让云端标记已失败候选，但本地不能绕过 queue 自行换策略。
   Client 对同 session 的下一次 poll 是放行下一策略的明确事实；在该 poll 发生前，Cloud producer 必须保持暂停。

4. 如果用户停止、pause 触发、session 超时、云端返回 invalid、坐标越界或消费到 `END`，本地按失败/取消处理，并异步上报 outcome。
   不能为了“继续跑”自动恢复旧本地生产 pipeline。

5. 云端收到 success/cancel/final-fail 后，应停止生产或让该 session 的剩余消息失效。
   本地也必须忽略过期 sessionId、窗口不匹配、任务不匹配或 round 不匹配的旧消息。
   仅从 session 索引中删除记录不算停止生产；已经持有 session 引用的 producer 也必须收到终止信号并退出。

## 明确禁止

1. 禁止把旧本地 pipeline 删除掉。
   它必须保留为 shadow/reference/testcase replay 依据，但生产不做 full fallback。

2. 禁止云端只做一套半等价 raw image 识别，然后直接返回一个最终点击点就结束。
   云端必须按旧 pipeline 顺序逐段生产候选，且每段要能在 testcase replay 中单独证明。

3. 禁止本地在生产路径里私自决定 fallback 顺序。
   本地只能消费 queue 消息、执行点击、验证 outcome、继续消费或结束。

4. 禁止把 post-click dialog option 处理塞进 NPC Click。
   NPC Click 只负责“这次 NPC 点击是否成功”，后续 dialog 选项由 dialog/任务业务处理。

5. 禁止用“每步都重新截图”替代 base screenshot session。
   普通 NPC click 主链路只截一次 base screenshot。确实需要特殊截图的场景必须另开设计，不得作为 CR169 的默认行为。
