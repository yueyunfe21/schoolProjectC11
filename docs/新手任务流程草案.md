# 新手任务流程草案（待审核，非正式业务逻辑）

> 状态：已根据首轮批注修订。本文仅是编辑中的业务草案，尚未进入 `docs/业务逻辑.md`，不授权直接实现。
>
> 坐标规则：本文所有屏幕点击点与 ROI 均以当前参考窗口的**屏幕绝对坐标**记录，参考 base 为 `(991,369)`。实现时一律换算为窗口相对坐标：`relativeX = absoluteX - baseX`、`relativeY = absoluteY - baseY`。运行时再由当前窗口 base 还原为实际屏幕位置。唯一例外是游戏地图坐标，例如 `(23,201)`，它不是屏幕坐标，不参与减 base。

## 1. 总体运行模型

任务名暂定“新手任务”。整体为一个持续 `while` 循环，但不是前台傻等：

1. 启动后立即关闭 runner 的自动战斗执行与自动补 `Alt+8`；**保留**战斗状态检测。
2. 截图、Tracker/option/title/模板识别、面板 hash 对比、移动状态观察和计时都在后台完成。
3. 后台发现可执行事实后，经 EventBus 唤醒当前任务；只有真正需要键盘/鼠标的原子动作才占用前台输入队列。
4. 不需要前台鼠标时，任务必须让出前台，和五环一样先提前计算，再由事件唤醒处理鼠标。
5. 任务总有效运行时长上限为 `1h`。暂停期间的时间必须补偿，即暂停时间不计入这 1 小时。
6. 暂停后恢复：先关闭所有 generic window，再直接重新进入主 `while` 循环；不尝试猜测暂停前执行到了哪一步。
7. 模板匹配默认阈值为 `0.85`，除非某个节点后续另行明确覆盖。

### 1.1 主循环优先级

每轮按以下顺序判断：

1. 若有 `option dialog`：点击**第一个选项**。只有点击 option 才可能触发动画。
2. 若当前已停止移动、且没有 option、且左侧 Tracker 中存在一个或多个绿色链接：按界面从上到下依次尝试绿色链接。
3. 绿色链接点击后，必须进入该链接专属的完全 `PARK`；单纯点击绿色链接不会直接改变 Tracker 面板内容。
4. 该 `PARK` 期间，主循环只允许因 `PREPARED_ACTION_READY` 醒来并消费一个可执行动作；任何普通观察事实均不得直接重新执行主循环或再次点击绿色链接。
5. 若正在移动：park，不干预。
6. 若未见 Tracker：不主动点击，可能在播放动画；仅运行本草案定义的 `ESC` 与小地图消失 `mouse` 检查。

### 1.1.1 Tracker 绿色链接的唯一唤醒契约（硬规则）

绿色链接是一次本地原子点击，但点击后的推进权必须唯一。禁止让 Cloud 主循环、本地 retry worker、观察器或通用 EventBus 事件分别拥有“再点一次”的权限。

1. 本地点击一个 Tracker 绿色链接后，立即登记 `activeGreenLink`，随后**完全 park**。在该状态清除前，主循环不得重新读 Tracker、不得派发同一链接、不得因为任意 `TASK_ATTENTION_REQUIRED` 重新运行普通绿链分支。
2. `activeGreenLink` 的主循环唤醒源只有 `PREPARED_ACTION_READY`。被唤醒时必须有一个带唯一 action id、可被本地实际执行的 `PreparedAction`；没有动作就不得唤醒。
3. runner 继续在后台观察，但观察本身只产生事实，不能直接推动鼠标：
   - 若看到 dialog：把 dialog 截图/事实提交 Cloud。Cloud 完成识别和业务判断后，必须封装为 `PreparedAction`（例如点击 option 第一项）并发布 `PREPARED_ACTION_READY`。
   - 若发现窗口停止且没有 dialog：上报 `PATHING_TERMINAL` 给 Cloud。`PATHING_TERMINAL` 本身**不能**唤醒新手主循环；Cloud 必须先根据当前 Tracker 内容、当前绿链记录和业务规则生成“重新点击/改点一个绿色链接”的 `PreparedAction`，再发布 `PREPARED_ACTION_READY`。
   - 若发现开始移动：仅更新移动观察；继续 park，不得发起新的 Tracker 点击。
4. 特殊 title、`ESC`、`esc_bot`、领养状态、恢复器状态、战斗状态等也都只是观察事实。若它们确实要求输入，Cloud 必须先生成对应 `PreparedAction`；若没有动作可做，则不得唤醒主循环。
5. `TASK_ATTENTION_REQUIRED` 不得进入 `activeGreenLink` 的 wake 集合。诸如 `xinshou-esc-bot:absent`、`xinshou-adoption:absent`、`xinshou-local-recovery:idle`、`dialog-visible:*` 只允许更新状态或促使 Cloud 产出 prepared action，不能直接解除 park。
6. 一个 `PreparedAction` 只能消费一次。消费后：
   - 点击 option：等待 dialog 内容或 Tracker 整体内容发生新的有效变化，再由 Cloud 决定下一动作；同一 dialog 指纹不得重复点击。
   - 重新/改点绿色链接：替换或重新登记 `activeGreenLink`，再次完全 park。
7. 因此“窗口被唤醒”严格等价于“窗口现在有一个必须执行的动作”；没有可执行动作时，窗口必须保持 park。

### 1.1.2 观察、取证、决策与执行的唯一职责

新手任务不是 Cloud 盲目轮询，也不是 Client 自主执行业务。完整链路固定如下：

1. **Runner 是初始事件源。** Tracker、dialog、特殊 title、战斗或寻路状态发生有效变化时，
   由 Runner 首先发现并上报。Runner 可以在首次上报中同时携带当前共享帧裁出的 ROI，减少一次往返。
2. **Cloud 是唯一业务决策者。** Cloud 收到初始事实后接管该事件；它可以直接使用随事实上传的图片，
   也可以根据已经明确的业务阶段继续向 Client 请求指定 ROI/图片。Cloud 的主动请求是有上下文的取证，
   不是在没有本地事件和业务阶段时盲目截图轮询。
3. **Client 必须回答 Cloud 的取证请求。** 由于 Client 不暴露入站接口，传输上允许由 Cloud 在
   observation response 中携带 `FrameDemand`，Client 在后续 observation request 中上传与
   `demandId + taskRunId + originatingSeq` 精确绑定的图片。旧任务、旧 sequence 或不匹配 demand
   的图片不得参与当前决策。
4. **取证过程不唤醒主任务。** title 事实、图片上传、模板未命中和“仍需下一张图片”都只在后台更新
   状态。Cloud 可以继续发出下一次 `FrameDemand`；在没有生成可执行动作之前，新手主循环保持 park。
5. **只有 Cloud 能创建业务 `PreparedAction`。** Cloud 取得足够证据并确定下一步后，写入一个带
   唯一 action id 的 `PreparedAction`，再发布 `PREPARED_ACTION_READY`。Dialog 动作优先于
   Tracker 动作；同一 observation generation 不得同时发布两种竞争动作。
6. **存在两层、含义不同的消费：**
   - Cloud 新手任务原子消费 Cloud 侧唯一 `PreparedAction`，校验 `taskRunId`、窗口、sequence、
     优先级和一次性语义，然后把它转换为 Client command；
   - Client 本地输入队列只消费 Cloud 已授权的 command，负责 exact-window 绑定、输入原子性与
     `SUCCESS/FAILED` 回执。Client 不得直接消费业务 `PreparedAction`，也不得根据 title 自行启动
     背包、给予、修复、导航或其他业务宏。
7. **本地模板匹配只是证据。** Runner 可以本地匹配确定性图片并上报候选模板、候选点或 presence；
   但除非本节或具体节点明确登记为机械级特例，任何真实键鼠动作仍必须先由 Cloud 形成
   `PreparedAction` 并下发 command。
8. **驱动关系总结：**未知画面变化由 Runner 主动推送；Cloud 接管后可主动向 Client 继续索取证据；
   业务判断始终在 Cloud；物理执行始终由 Client 被动完成。

### 1.1.3 无推进时的观察重举证

1. 没有 active pathing 时，Runner 仍须每个 observation tick 检查同一份 shared cycle frame，
   并将本次 Tracker/Dialog/title 观察与上一次**本地 tick**比较；Cloud ACK 去重不能阻止本地继续检查。
2. 观察发生有效变化时立即上报，并重新开始无推进计时。
3. 连续 `10s` 没有有效推进时，Runner 在一个 observation request 中重举证本轮 shared frame
   对应的当前 Dialog/Tracker 观察；不得为 Dialog 和 Tracker 分别再截图或再发请求。
4. Cloud 收到重举证后自行结合当前特殊 title/业务状态裁决。一轮只允许一个结果：
   有 Dialog 时只处理 Dialog；没有 Dialog 时才处理 Tracker；没有可执行动作时保持 park。
5. Cloud 选择继续处理特殊 title、暂不发布动作，不会永久关闭恢复入口。若画面仍无推进，
   Runner `10s` 后再次提交最新观察，Cloud 必须重新裁决。
6. 本地 timeout 只授予“重新举证”权限，不授予任何点击、清 UI、重试链接或业务跳转权限。

### 1.2 推进成功的判定

点击 option 后，不比较单条绿字是否变化，因为同一个 NPC 名称可能重复出现。应当比较**整个 Tracker 面板内容**的 hash：

- hash 变化：视为前一步已推进，继续执行新的 Tracker 链接。
- hash 未变化：保持循环观察；不要凭单条绿色文字相同就认定失败。

### 1.3 一次性标题节点

本文所有 title 专属处理都是一次性动作。某个 title 对应的业务动作已成功处理后，后续循环记录为“已消费”，直接跳过该 title 的专属模板识别，仍继续通用 Tracker / option 循环。

### 1.4 已验证资产白名单

架构返修默认不保留现有实现；只有以下三项已有明确实机或回放依据，必须原样保护其业务语义：

1. **领养绿色链接单击锁：**`lingyang_title.png` 首次绿链点击后锁定，确认领养真实点击、
   title 改变或 `30s` 超时才释放。完整规则见 §3.1。
2. **独立 Dialog 识别：**保留 `DialogFrameClassifier` 对完整 Dialog 外框 presence 和
   `SMALL/MEDIUM/LARGE/UNKNOWN` 尺寸的独立判断，以及当前已经通过的 SMALL 两种 lower ROI
   回放结果。该白名单只保护识别算法，不授权旧的同步轮询、错误唤醒或重复点击链路。
3. **抓捕战斗动作：**保留 §4.2 的 `Alt+B -> 自动面板消失验证 -> 已验证固定坐标点击` 顺序和
   点击位置。架构调整可以改变它如何获得 `PreparedAction`，但不得改变按键、验证条件、坐标和顺序。

白名单以外的现有新手代码不视为已验收。绿链调度、Dialog prepared/wake、title 本地宏、恢复器、
拖拽会话、暂停/停止生命周期和现有测试均须按 §1.1.1、§1.1.2 重新审核后决定保留、替换或删除。

### 3.1 领养 title 的绿色链接单击锁

该锁是已经批准的业务规则，架构返修时必须保留：

1. 仅当当前 title 为 `lingyang_title.png` 时生效，不得扩展到其他新手节点。
2. 第一次真实下发 Tracker 绿色链接点击后立即锁定；锁定期间禁止再次生成或执行同一领养绿链点击。
3. 锁属于 Cloud 当前 `taskRunId` 的任务状态，Tracker hash、普通 observation 刷新或本地状态重置
   均不得清除它。
4. 满足任一条件时释放：
   - “确认领养”动作已被真实执行，并由单调递增的确认点击计数证明；
   - Tracker title 已不再是 `lingyang_title.png`；
   - 自首次绿链点击起已满 `30s`。
5. 锁释放只允许 Cloud 重新评估是否能生成新的 `PreparedAction`，不得直接触发本地补点。

## 4. 战斗控制与“抓”标题

- 触发 title：`images/template/xinshou/zhua_title.png`。
- 该 title 下仍按主循环点击 Tracker 绿色链接和 option 第一项，由此进入战斗。

### 4.1 抓捕 title 前的任意普通战斗

新手任务启动时关闭 runner 自动战斗执行与自动补 `Alt+8`，但保留 runner 的战斗进入/退出判断。

在“抓” title 尚未完成之前，任意检测到进入的普通战斗均执行：

1. 检测到进入普通战斗后不增加固定等待，立即准备本轮自动战斗动作。
2. 每轮自动战斗动作必须在同一个 frozen exact-window focused transaction 内线性按两次
   `Alt+A`，两次之间不增加额外等待。
3. 本轮执行成功后每 `5s` 再执行一轮双 `Alt+A`，直到战斗结束；执行失败仍按既有
   `1s` 有界重试。
4. 此阶段不恢复 runner 自动战斗，也不恢复自动补 `Alt+8`。
5. `IN_COMBAT` 至 `COMBAT_EXITED` 期间由本节独占新手动作槽；Dialog、Tracker、
   title 与进战前寻路事实只能后台更新，不能替换战斗动作或触发绿链点击。
6. 收到 exact `COMBAT_EXITED` 后立即结束战斗独占；进战前或战斗中遗留的寻路事实不得阻断
   脱战后的新鲜 Dialog/Tracker `PreparedAction`。

### 4.2 抓捕战斗本身：保留 `Alt+B`

抓捕 title 下按主循环点击 Tracker 绿色链接、option 第一项并进入战斗后：

1. 执行原定的 `Alt+B` 操作。
2. 复用现有 runner 的自动面板判断：`Alt+B` 后看不见“自动”按钮即为成功；仍看得见则重试 `Alt+B`。
3. `Alt+B` 生效后，鼠标移动至参考屏幕坐标 `(1246,777)` 并左键点击一次。
4. 等待抓捕战斗结束；本段不使用普通战斗的“每 `5s` 双 `Alt+A`”规则。

### 4.3 抓捕完成后的下一场战斗

1. 抓捕 title 已完成后，下一次检测到进入战斗时，按两次 `Alt+A`，间隔 `1s`。
2. 复用现有 runner 的自动面板判断：两次 `Alt+A` 后重新看见“自动”按钮即为成功；未看见则重试该恢复操作。
3. 成功后恢复 runner 自动战斗执行与自动补 `Alt+8`。
4. 此后的战斗全部恢复既有自动战斗逻辑。

## 10. “修复”标题：三件物品放入

### 10.2 三件物品与三个槽位

物品选择参考屏幕坐标：第一件 `(1482,973)`、第二件 `(1533,964)`、第三件 `(1586,950)`。

每一件均执行：

1. 左键选择物品。
2. 按五倍接任务后浮窗的既有延迟/识别方式，等待浮窗稳定后依次尝试三个槽位 `(1301,839)`、`(1395,887)`、`(1446,890)`。
3. 每次槽位点击后匹配 `images/template/xinshou/xiufu_fangru_suc.png`：该图表示“放入槽位后出现的成功浮窗”。
4. 命中该图：当前件成功，直接选择下一件；不会再次选择当前件。
5. 三个槽位都未匹配到该浮窗时，对当前件执行 fallback：重新选择该物品，再按原顺序尝试三个槽位。
6. fallback 的每次槽位尝试只要匹配到 `xiufu_fangru_suc.png` 即视为当前件成功，随后才处理下一件。

### 10.3 完成与整体重试

1. 三件都已尝试后，匹配 `images/template/xinshou/xiufu_alldone.png` 即视为完成。
2. 即使没有看到该完成浮窗，只要三件均已尝试，交由 runner 在后台判断 Tracker title 是否变化。
3. title 变化后等待 `1s`，再左键点击参考屏幕点 `(1663,589)` 关闭窗口，回到主循环。
4. 等约 `10s` title 仍未变化，则从第一件开始重新执行完整修复流程。
